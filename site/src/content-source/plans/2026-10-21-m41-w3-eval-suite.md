# Local `claude plugin eval` smoke suite (W1.7) Implementation Plan

**Goal:** Give the sdlc plugin a small, local, pre-release eval suite that runs real skills end to end and grades only the files they leave behind.
- Seven eval cases under `plugins/sdlc-utilities/evals/`, each with a prompt, a fixture scaffold and file-only graders.
- One shared fixture builder, `evals/_fixture/build-fixture-repo.js`, that every case's scaffold calls.
- `plugin.json` declares the suite (`experimental.evals`), and `schemas/plugin.schema.json` accepts that field.
- `tests/promptfoo/README.md` documents the local run; `.gitignore` ignores the run results.

**Architecture:** The root problem is that the promptfoo suite never runs a skill the way a user does (real turns, real hooks, nested agent dispatch), so whole failure classes stay invisible until release. `claude plugin eval` runs the plugin in an isolated `claude -p` session against a scaffolded git repository; each case is a directory with `prompt.md` (run limits and the prompt), `case.yaml` (scaffold and graders) and `scaffold.sh` (a five-line wrapper around the shared Node builder). Graders are only `file_exists` and `regex` over `{source: file}` (ruling w17-design (a)); where the item asks for something no surviving file shows, the nearest file fact is graded instead and listed in the substitution table (ruling w17-ledger). The plan runs no credentialed command; the two owner-approved eval runs happen after the commit (Task 13).

## 0. How to execute this plan

This plan is written for an executor model that works **one item at a time with no memory of the review**. Rules:

1. Work in **milestone order** (§3). Inside a milestone, pick any item whose **Depends on** list is satisfied. Never start an item from a later milestone.
2. Before editing, read the item's **Files** and **Current state** and confirm every quoted line is present (`sed -n 'N,Mp' <file> | tr -d '\r'` — the working tree is a CRLF checkout; line numbers match HEAD). In quoted current-state text a backslash-backtick (`\``) is a backtick nested inside the quote, not part of the file. Line numbers are HEAD (`0c0cdcc`). When an earlier item or sub-item has already edited the same file, locate each quoted line with `grep -n` and proceed only if it occurs exactly once; apply multi-site edits within one item bottom-up (highest line first). If a quoted line, path, subcommand or flag cannot be found that way, **stop and report** the discrepancy. Do not search for an alternative and do not guess.
3. Apply **only the Change**. Leave everything under **Must not touch** byte-identical. Do not "improve" adjacent text.
4. Run the item's **Verification** commands and compare with the stated expected result. Testing policy (AGENTS.md): promptfoo only, never `node:test`/Jest. Exec-only configs (`tests/promptfoo/promptfooconfig-exec.yaml`, `promptfooconfig-exec-hooks.yaml`) may be run targeted at any gate with `--filter-pattern`. Never run the full behavioral suite (`promptfooconfig.yaml`); at most **one** targeted behavioral case as the final check. No run-fix-rerun loops.
5. Update the named promptfoo **dataset** under `tests/promptfoo/datasets/` when the item says so (new behaviour → new case; changed strings → changed assertion). Every new case's `description` starts with the item's `--filter-pattern` string followed by `: `, so the targeted run selects it; `--filter-pattern` is a regular expression, so escape `(`, `)` and `+`.
6. Commit per item with the repository convention `type(#issue): skill - description` (e.g. `fix(#NNN): ship-sdlc - remove worktree gotchas`), ending the message with the attribution line the session provides. Do not commit on `main`.
7. Keep `R<n>` / `R-slug` spec anchors in SKILL.md text; drop GitHub issue numbers from model-facing prose; state each rule once with its reason.
8. If an item's **Change** contradicts the code you find (a function already exists, a flag already parsed, a spec line already removed), stop and report. The plan is not the source of truth; the code is.
9. After M3, if your item edits the SKILL.md or spec of a skill whose `docs/specs/<skill>.md` has no `## Inputs and flags` line, first do W3.5 for that spec in a separate commit.

## Context

**What problem does this change solve?**

- The promptfoo suite checks prompts and scripts, but it never runs a skill the way a user does.
- So it cannot see failures that only appear in a real session: a turn that ends too early, a hook that blocks at the wrong moment, or a nested agent dispatch that loses a flag.
- `claude plugin eval` (Claude Code's built-in eval runner for plugins) runs the plugin in a fresh, isolated session against a small scaffolded repository and grades the result.
- This plan adds a small smoke suite for it: seven cases that each run one skill once and check the files it leaves.

**What prompted this change now?**

- Design review recommendation #6 and §F step 2 (maintainer decision D3: local only, never in CI).
- Todo #9129: inside ship, review-sdlc runs without `--auto`. If it stops before writing its summary file, ship's review gate always dispatches received-review. The owner wants an eval case that shows whether a clean review leads ship to skip received-review. Its result decides a later spec change (ship R7). That change is not part of M4.1.

**What does success look like?**

- Seven case directories exist, each with a prompt, a scaffold and at least one grader.
- Every scaffold builds its fixture locally, with no model, in a few seconds. The repo it builds is within the owner's size limit (at most about 5 tracked files and about 50 lines).
- `plugin.json` declares `experimental.evals`; `claude plugin validate` and a schema check both pass.
- `tests/promptfoo/README.md` explains how to run the suite locally and what it costs.
- After the commit, `commit-auto` passes once in a direct headless run graded by its own graders, and the `ship-review-zero-findings` result is recorded as it is. The `claude plugin eval` harness run waits for a host with bubblewrap and socat (follow-up #9150, ruling w17-sandbox).

**Who fails if this ships wrong?**

- The executor of the two credentialed runs: a broken scaffold or a grader that can never pass wastes a paid run, and only one environment-only re-run is allowed.
- The owner, who reads the #9129 result to decide the R7 change. A grader that passes for the wrong reason would mislead that decision.
- Plugin users only indirectly: `evals/` ships with the plugin directory, and a schema mistake in `plugin.json` could produce a validator warning when the plugin loads.

**Non-goals (deliberately not built):**

- No CI wiring: no workflow runs the suite (D3, item guardrail).
- No promptfoo case, dataset or config change (plan-source rule).
- No change to any skill, script, hook, agent or spec.
- No observed-skip grader for #9129. Copying the step envelope is follow-up #9149 (ruling w17-ledger, option B).
- No edit to `docs/architecture.md` or `AGENTS.md`, although two of their lines become incomplete (follow-up #9148; see Research Findings).
- No `ship-resume` case (item case 6): it is not gradable by files in a single non-interactive run (Key Decisions KD3).
- No release: no version bump, no CHANGELOG entry, no tag (those belong to the orchestrator's release phase, not this plan). That release is 0.30.0 from 0.29.1 (ruling w3-plan m4).
- No R7 `--auto` forwarding change (plan source).

## Key Decisions

- **KD1 — File-fact substitutions (ruling w17-design (a), w17-ledger).** Graders read only files the plugin's own code or git writes. Each item grader maps as follows; the PR copies this table.

  | Case | Item grader | File grader(s) | Why |
  |---|---|---|---|
  | commit-auto, crlf-checkout | HEAD commit exists | regex `\tcommit: ` with `count:1` on `.git/logs/HEAD` (unverified, U2) | git writes one reflog line per commit |
