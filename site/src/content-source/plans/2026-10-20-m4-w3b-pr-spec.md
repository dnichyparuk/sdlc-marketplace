## Key Decisions

**Problem in one sentence:** the pr-sdlc spec is still a change log, and the "restructure on next touch" rule requires it to become a contract before W4.4 edits pr-sdlc.

- **Move, don't rewrite.** Each block moves byte-for-byte. Only the listed lines change. A reader can then check the commit with a sorted line diff (P-6) instead of reading every sentence.

- **Placement follows the default rule, with three named exceptions.** The W3.5 default puts an R-id by what it names: a flag or config key goes to Inputs and flags, a must-not or always property goes to Invariants, and everything else goes to Step composition. Three R-ids are hard checks before publishing, so they go to Gates instead. R16 is part of a failure path, so it goes to Failure handling. The Deviations table records each exception.

- **Sub-headings mirror the review-sdlc restructure.** The same names make the specs read alike, and the restructured review-sdlc spec shows that the validator accepts them.

- **No behaviour change.** No SKILL.md, script or test changes. The W4.4 spec consequences come in plan 2 (`2026-10-20-m4-w3b-openspec-specs.md`).

- **Non-goals.** No other spec is restructured. `site/src/content-source/**` is not hand-edited; copy-docs runs once after the third ship run. The `validate-spec-shape.js --strict` switch waits until the last of the ten legacy specs lands (W3.6).

- **Failure audience.** Spec readers and every SKILL.md, agent file or test that cites a pr-sdlc id. A lost or renamed id breaks those citations; P-5 and P-7 catch it.
