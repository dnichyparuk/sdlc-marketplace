# plan-sdlc Specification

> Decompose requirements into a classified, dependency-ordered implementation plan with per-task metadata ready for execute-plan-sdlc consumption. Designated plan-mode skill.

**User-invocable:** yes
**Prepare script:** `skill/plan.js`

## Inputs and flags

- A1: `--spec` — include OpenSpec context in planning (default: false)
- A2: `--from-openspec <change-name>` — load a specific OpenSpec change directly, bypassing the gate check (default: none)
- A3: `spec-file-path` — path to a spec or requirements document (positional)
- A4: `--quality full|balanced|minimal` — plan-review quality preset: sets the model and effort of the Step 5 lens reviewers and the single reviewer (R8); resolved by `plan.js` into `flags` (P24); an invalid value is an `errors[]` entry and exit 1 (default: `balanced`)
- R2: In plan mode, always write to the designated plan file path
- R3: In normal mode, resolve output path via: user-specified → `plansDirectory` from settings → default `~/.claude/plans/`
- R10: When `--from-openspec` is passed with a valid change, use `tasks.md` as the primary decomposition skeleton
- R16: When `openspec/config.yaml` exists AND the injected session-start `<system-reminder>` contains a contradictory signal (regex matching `not initialized` together with `openspec`), the skill MUST emit a single audit line naming the authoritative file path and note that the contradictory signal is being ignored. The override line is informational only — skill flow continues. (Rationale: defensive hardening against co-installed plugins emitting false-negative OpenSpec detection.)
- R61 (replaceable template): Projects can replace the default plan template entirely via a project-level `.sdlc/plan-template.md`. `plan.js` always emits a `planTemplate` object; its `path` is the absolute path to the project override when the override file exists on disk, or `null` when it does not — the object is never omitted, only `path` varies (P21), with no further resolution chain. When null, the skill falls back to the plugin's shipped default template, a sibling file in the skill directory (`plan-template-default.md`). The active template — project override when present, shipped default otherwise — is the single source PF10 reads, and the source the Step 2 planner follows when writing plan sections. The default template MUST declare `## Context`, `## Final Shape`, `## OpenSpec Appendix`, `## Contract Examples`, `## Deviations & assumptions`, and `## Verification Scorecard` as required section headers, so R57-R60, R47, and R40/R44 are satisfied out of the box for projects that never customize the template. This is a floor, not a ceiling: the shipped default template MAY declare additional required sections beyond this minimum (it currently also declares `## Research Findings` and `## Key Decisions`, both narrative-style, to capture exploration context and the rationale behind non-obvious choices) — those extras are template content, not spec-mandated headers, so PF10 enforces them only because they're listed in the active template's `## Required Sections`, not because any R-number requires them. A project override is free to drop, rename, or add to them (a project override MAY, for example, drop `## Research Findings` in favor of tracking it elsewhere, as long as the six spec-mandated headers above remain).
- R-config-version: The prepare script `skill/plan.js` MUST call `verifyAndMigrate(projectRoot, 'project')` at start. The call is short-circuited when CLI `--skip-config-check` OR env `SDLC_SKIP_CONFIG_CHECK=1` is present; both gates resolve into a single `flags.skipConfigCheck` boolean in the prepare output (CLI > env > default false). On migration failure the prepare emits non-zero exit and an `errors[]` entry naming the failing step; SKILL.md halts with that text verbatim.
  - Acceptance: prepare output includes `flags.skipConfigCheck` and a `migration` block (or null when skipped); SKILL.md gates further work on `errors.length === 0`.

## State model

- R20: planIntegrity markers — `plan-sdlc` MUST write four checkpoint markers into a per-branch plan state file at `.sdlc/execution/plan-<branchSlug>-<ts>.json`. State file JSON schema: `{ "planIntegrity": { "skillInvoked": "<ISO-ts>", "planFile": "<ISO-ts>", "guardrailsEvaluated": "<ISO-ts>", "critiqueRan": "<ISO-ts>" }, "planFilePath": "<abs-path>" }`. Write sites: (1) `skillInvoked` — written by `skill/plan.js --output-file` at Step 0 prepare (skill was invoked); (2) `planFile` + `planFilePath` — written by `skill/plan.js --mark plan-file --path <abs>` after Step 0 path resolution in both plan-mode and normal-mode branches; (3) `guardrailsEvaluated` — written by `skill/plan.js --mark guardrailsEvaluated` at the end of the Step 3 guardrail-compliance gate; (4) `critiqueRan` — written by `skill/plan.js --mark critiqueRan` as the final action of Step 3. Each marker value is an ISO 8601 timestamp; presence of a key means that checkpoint was reached. The `planFilePath` sibling field stores the absolute path to the written plan file, enabling downstream consumers to stat the file for non-empty content verification.
  - **Lifecycle:** (a) **Prune-on-write** — `pruneStateFiles('plan', branchSlug)` MUST be called immediately before `initState('plan', …)` in the `--output-file` branch of `skill/plan.js main()`. This ensures at most one `plan-<branchSlug>-*.json` file exists per branch between plan-sdlc invocations. The call is wrapped in the same try/catch as `initState` so a prune failure cannot block prepare output. The `--mark` branch MUST NOT prune — it reads the existing marker via `findStateFile` and would break if its target were removed first. (b) **Consume-then-delete** — `hooks/stop-plan-integrity.js` MUST capture the marker file path from `findStateFile` before reading, evaluate all integrity checks, then call `deleteState(path)` regardless of integrity outcome (single-shot semantics). The unlink is wrapped in a try/catch so a failed delete cannot turn into an internal error. After consume, subsequent Stop events on the same branch find no state and exit 0 — this is correct R21 behavior (the marker is single-use per plan-sdlc invocation). (c) **GC orphan sweep** — stale plan markers (TTL-expired or branch-deleted) are removed by `ship-sdlc --gc` and `execute-plan-sdlc --gc` via `gcStateFiles({ prefix: 'plan', … })`. Each `--gc` call site MUST invoke `gcStateFiles` a third time with `prefix: 'plan'` and include a `plan` field in the aggregated JSON output so downstream consumers see all three buckets (`ship`, `execute`, `plan`). (d) **Atomic write** — plan state files inherit `atomicWriteSync` from `scripts/lib/state.js`; no partial-file states are possible.
- R21: stop-plan-integrity hook contract — a `Stop` hook MUST verify plan integrity at session end from the plan state file. If a plan state file exists for the current branch, the hook reads it, collects missing markers from `planIntegrity` (any of the four keys absent), and additionally stats `planFilePath` (if set) treating an absent or empty file as a failed `planFile` check; if any check fails it emits a structured stderr warning naming each missing checkpoint (`[plan-integrity] WARNING: Plan presented with incomplete plan-sdlc execution. Missing checkpoints: <list>`), one detail line per missing checkpoint. The hook MUST exit 2 with the warning on stderr when any marker is missing (so the model sees it), and exit 0 on every other path including any internal error. With no plan state file the hook exits 0 silently and reads no stdin. Unexpected errors are swallowed by a top-level try/catch with silent exit 0.

## Step composition

### Phases

1. SETUP — mode detection, routing, OpenSpec integration, complexity routing, guardrail loading via `skill/plan.js`
   - **Script:** `skill/plan.js`
   - **Params:** `--from-openspec <name>` (from A2) when applicable
   - **Output:** JSON → P1-P7 (openspec detection/active changes/branch match, from-openspec validation/delta spec count/tasks presence, plan guardrails array)
2. CONSUME — requirements discovery, codebase exploration, OpenSpec enrichment
3. PLAN — decompose into tasks with per-task metadata, key decisions, file structure mapping
4. CRITIQUE — self-review against all 21 quality gates
5. IMPROVE — autonomous fix loop; apply Step 3 self-critique findings and Guardrail Compliance updates; no user interaction.
6. CRITIQUE — plan review loop (cross-model, max 3 iterations; skip for lightweight)
7. IMPROVE — apply review fixes, re-dispatch reviewer
8. HANDOFF — announce plan path, present workflow continuation menu (execute/ship/done)

### Steps

- R1: Complexity routing: 1 file → skip (no plan needed), 2-3 files → lightweight (skip exploration and review loop), 4+ files → full pipeline
- R13: After exploration, re-read the plan file's Requirements section before decomposition (re-anchor to counter attention drift)
- R14: Remove the `## Requirements` working section after task decomposition (temporary scaffolding)
- R22 (single-touchpoint handoff): Step 7 (Handoff) is the SOLE user touchpoint for the finalized plan. Step 0 session-recovery and Step 4 approval gates MUST NOT prompt the user — both run autonomously. The Step 3 self-critique and Step 5 IMPROVE loop apply fixes (including Guardrail Compliance updates) without user interaction. Genuine user-decision gates that remain (and are explicitly preserved): (1) requirements gathering when the spec is missing or ambiguous, (2) scope-split prompts, (3) OpenSpec routing — including the inline-artifact-generation default (R63), (4) the Step 6 reviewer-loop max-iterations escalation, (5) the Step 4 error-severity guardrail-block harden offer (R19), (6) the Step 7 handoff menu, (7) ambiguity/multiple-viable-approach prompts discovered during planning (R65; suppressed under `--auto` — falls back to Key Decisions recording). Rationale: removes one premature checkpoint that operators cannot skip plus one redundant prompt that duplicates the Step 7 menu; downstream `--auto` automation needs deterministic non-interactive plan generation.
- R26 (Discovery brief artifact): The orchestrator writes `discovery-brief.md` to `manifest.outDir/discovery-brief.md` with stable `F-<DIM>-<n>` finding IDs. Code findings format: `F-<DIM>-<n>: file:line — observation`. Web findings format: `F-<DIM>-<n>: <url> — observation (recency, source-type)`. Hybrid findings are tagged `[web-only | verified-in-codebase | conflicts-with-codebase]`. When web/hybrid dimensions ran, the brief includes a `## Best-Practice Synthesis` section.
- R63 (OpenSpec gate default: inline artifact draft): The Step 0 OpenSpec gate's option 2 changes from "skip spec workflow, plan from conversation context" to **inline artifact generation**: draft the OpenSpec proposal, delta specs, and tasks list as an `## OpenSpec Artifacts (Draft)` appendix inside the plan file itself, then continue planning against that draft. This becomes the effective outcome whenever a functional change has no matching active OpenSpec change and the user does not choose to start the external OpenSpec flow or point at an existing change — replacing the prior "no spec" fork. Drafting MUST NOT invoke the `openspec` CLI and MUST NOT introduce any further interactive question at this gate — it proceeds autonomously, preserving R22's single-touchpoint principle. The drafted content populates the `## OpenSpec Appendix` section (R59) with the proposal/delta-spec/tasks prose. Because the draft is authored at Step 4 (Appendix generation) from exploration and decomposition data that does not exist yet at the Step 0 gate, `openspecContext` intentionally stays empty through Steps 1-5 for the inline-generate path — OpenSpec enrichment (Gate A, decomposition awareness, task annotation) does not activate for that path, exactly as it does not today for a plan with no OpenSpec source. This is a deliberate sequencing choice, not a gap: Step 0 lacks the exploration/decomposition inputs an accurate draft needs, so drafting is deferred to the step where those inputs are available, rather than producing a low-fidelity draft early. The script-derived structured fields — `openspecContext.requirements` (P18) and `openspecContext.tasks` (P13) — likewise stay `null` for an inline draft exactly as they do today when the CLI is absent or a change has no `tasks.md`; G11 and Gate A (R39) already fall back to their existing null-inventory paths (delta-spec text scan; Gate A skipped) in that case, so no new fallback is introduced. The appendix MUST be complete enough that `openspec create`/`openspec validate` can run directly off it after handoff, with no further interactive authoring step. Options 1 ("Start OpenSpec flow") and 3 ("Use existing spec") are unchanged.
- R65 (Ambiguity-triggered clarification): During Steps 1-2, whenever planning reaches a genuine fork — the requirements admit two or more materially different implementation approaches, or a scope/behavior decision cannot be resolved from the spec, prior conversation, or codebase precedent with reasonable confidence — the skill MUST ask via AskUserQuestion at the point the fork is discovered, rather than silently choosing one approach and recording it afterward. This sits below the coarser "spec missing or ambiguous" threshold already covered by R22 item 1: R65 covers narrower forks discovered mid-planning, not just an absent or single-sentence spec. A fork is NOT material when the alternatives are outcome-equivalent (naming, ordering, or other cosmetic choices) — those remain autonomous and may still be logged as an assumption. The `## Deviations & assumptions` section (R47) records decisions actually made, including ones the user was asked about; it is not a substitute for asking when a fork is material. Suppressed under `--auto`: the skill picks the most conservative approach autonomously and records the decision in `## Key Decisions` instead of prompting.

- P-STEP-1: Script returns universal envelope with `status`, `step`, `llm_decision`, `state_file`, `progress`, and `ext` fields on every invocation
- P-STEP-2: Script accepts `--after <step_id> --result-file <path> --state <state_file>` for subsequent invocations after the initial call
- P-STEP-3: State file is created on first invocation, updated after each step, and cleaned up when status is `"done"`
- P-TRANS-1: Step transition map — TBD (to be defined during script migration)
- P-TRANS-2: Every `step.id` in the transition map has a corresponding `When step.id == X` section in SKILL.md
- C-STEP-1: The LLM MUST NOT skip steps or reorder the sequence — the script controls progression
- C-STEP-2: The LLM MUST NOT read or modify the state file directly — it passes the path back to the script via `--state`
- C-STEP-3: When `llm_decision` is null, the LLM executes the step without asking the user or making judgment calls
- C-STEP-4: When `llm_decision` is non-null, the LLM MUST resolve it (via domain knowledge or user interaction) before proceeding

## Dispatch and routing

- R8: Plan review loop model rule: the Step 5 lens reviewers (plans with 5+ tasks) and the single reviewer (fewer than 5 tasks) run on the model and effort of the `--quality` preset (A4) — the "Plan quality presets" table in `docs/cost-tiers.md` §5 — which `plan.js` applies as `dispatchModel`/`dispatchEffort` on each reviewer entry (P17, P25); a null value means the agent file's own value. Under the default `balanced` preset `dispatchModel` is null and the reviewer runs on the model opposite to the plan author's (`opus` when the author ran on sonnet, otherwise the agent file's model). ≥1 reviewer per iteration; multi-reviewer fan-out within an iteration is permitted; iteration counter counts iterations, not reviewer dispatches; max 3 iterations
- R24 (Orchestrator dispatch): When `explorePack.manifestPath` is non-null AND complexity routing landed at full pipeline (4+ files), Step 1 dispatches `sdlc:plan-explore-orchestrator` exactly once. Lightweight scope (≤3 files) skips the orchestrator entirely and uses inline exploration as today.
- R25 (Dynamic dimensions): The orchestrator's SCOPE step emits 3–5 kebab-case task-specific dimensions in JSON `{ name, description, files[], mode, model }`. Names MUST NOT be the literal generic axes "architecture" / "tests" / "security" alone — they must be task-shaped (e.g., `auth-middleware-integration`, `cli-flag-parser-refactor`).
  - R25a (Web-mode rules): When `explorePack.webResearchSignal` is true OR the task involves a novel external technology, the orchestrator MUST emit ≥1 dimension with `mode: web` or `mode: hybrid`. Per-mode budgets: `web` ≤5 searches + ≤8 fetches; `hybrid` ≤3 searches + ≤5 fetches. Web dimensions are FORBIDDEN for pure internal refactors (when `webResearchSignal` is false AND the prompt indicates rename/move/dead-code removal).
- R37 (Step 1 inline-fallback parallel dispatch): When the orchestrator path is skipped (lightweight scope ≤3 files or error fallback per R28), inline exploration MUST issue its Glob/Grep/Read calls in a SINGLE message (parallel dispatch). Mirrors the in-skill precedent at SKILL.md OpenSpec artifact reads (`Read in parallel: …`).
- R56 (orchestrator await barrier): The `plan-explore-orchestrator` agent MUST block until every dispatched discovery-dimension subagent returns before consolidating. (a) no Step 2 dispatch passes a `run_in_background` parameter (the Agent tool has none); subagents run in the background and notify the orchestrator when they complete, and awaiting those notifications is the barrier; (b) the turn is not complete and the orchestrator MUST NOT enter Step 3 (CRITIQUE) or write `discovery-brief.md` until it has collected exactly one result per dispatched dimension — N = count of dispatched discovery dimensions; (c) if the runtime backgrounds a dispatch and re-invokes via task-completion notifications, it keeps awaiting across notifications until the collected count equals N. Consolidating on partial or zero results is forbidden.
- R31 (G17 Dimension Coverage gate, advisory): At Step 3, `plan.js g17-prepare` (R67) reads the plan file, all `.sdlc/review-dimensions/*.md` and `.github/instructions/*.instructions.md`, matches the plan's Create and Modify paths against the trigger globs, evaluates the CREATE criteria (C1–C6) and the path/structure UPDATE criteria (U1–U6), and applies the suppression rules and the learnings deferral below. plan-sdlc then dispatches a dedicated Agent subagent in parallel with the other lanes, the plugin agent `plugins/sdlc-utilities/agents/plan-lane-g17.md` (dispatched from `g17Dispatch`, P15), unless the script found no candidate and no covered dimension; the subagent evaluates the behavior-modification UPDATE criteria (B1–B4) and writes one `why` sentence per candidate. `plan.js merge-lanes` (R67) ranks, caps and renders the findings, each tagged with severity hint, criteria-triggered list, and dimension name. Every accepted proposal carries an X1 Copilot-mirror sync clause when P14.githubHosting.detected is true. Suppression rules: no CREATE for single-file diffs unless C3/C4 fires; no UPDATE for doc-only diffs (`docs/**`, `README*`, `*.md` outside skills); no B-criterion for pure refactors (rename-only, formatting, type-narrowing); cap at 3 proposals ranked by `(severity_rank DESC, criteria_count DESC, dimension_name ASC)` with `_N additional candidates suppressed_` annotation; defer when `.sdlc/learnings/log.md` shows a recent (within active PR commit window) `harden-sdlc` entry whose `Dimensions:` line names the candidate dimension. Severity classification: **advisory** — G17 emits findings but never blocks plan finalization; absent proposals do not fail the critique gate. **Dispatch-failure fallback:** if the G17 Agent dispatch errors, times out, or returns malformed JSON, treat the result as empty findings and continue to Step 4 — never block plan finalization on a G17 subagent fault. Log the failure to `.sdlc/learnings/log.md` for visibility. **Prepare-failure fallback:** a non-zero exit of `plan.js g17-prepare` does not stop plan-sdlc (E9): G17 is not run — the dimension-coverage lane is not dispatched and is left out of `--lanes`, the failure is logged to `.sdlc/learnings/log.md`, and every Step 5 `merge-lanes` call of the run passes `--g17-not-run`, so the Gate B scorecard shows G17 as not run with a WARNING (R67). Latency baseline — pre/post mean of 3 plan-sdlc invocations on a representative full-pipeline plan MUST be recorded in the PR description; G17 dispatch overhead documented per the latency-baseline task in the implementing plan.
- R33 (P15 g17Dispatch metadata): `plan.js --output-file` MUST emit `g17Dispatch` in the agent-dispatch shape (P15) for the agent `sdlc:plan-lane-g17`. `agentPath` is the absolute path of `agents/plan-lane-g17.md` next to the running `plan.js` (`<plan.js dir>/../../agents/`), or null when that file is absent; no other location is searched. `model` and `effort` are read from that file's frontmatter. SKILL.md's Step 3 dispatch of the dimension-coverage lane MUST use `subagent_type: <entry>.agent` and build the prompt from `inputNames`/`presetInputs` (`agent-dispatch-script-driven` guardrail).
- R35 (Step 3 lane fan-out): Step 3 (CRITIQUE) dispatches four lane subagents IN PARALLEL in a SINGLE message at the start of Step 3. Lanes own disjoint gate subsets per KD1: (a) **static-structural** → G1, G2, G7; (b) **content-coverage** → G5, G6, G8, G9, G11, G13, G15, G16, G18, G19, G20, G21; (c) **guardrail-compliance** → G14; (d) **dimension-coverage** → G17 (R31). `validate-plan-format.js`, run before the dispatch, owns G3 and G12 (PF4), G4 (PF12) and G10 (PF13). The guardrail-compliance lane is not dispatched when `guardrails` (P7) is empty; `plan.js merge-lanes --no-guardrails` then supplies its constant result `{ gateIds: ["G14"], issues: [], passes: ["G14"], laneStatus: "ok", guardrailCompliancePayload: "No active guardrails configured." }`. Each lane returns the normalized schema `{ gateIds: string[], issues: [{ gateId, severity, taskRef, message, blocking }], passes: string[], laneStatus: "ok"|"failed"|"timeout" }` (the dimension-coverage lane returns `{ candidates: [...] }`, R31). The skill writes each lane's JSON to `<critiqueDir>/iter-<k>/<lane name>.json` (P22), and `plan.js merge-lanes` (R67) merges the lane results with the validator report: gate coverage union {G1..G21}, lane-failure issues, dedup. Each lane is a plugin agent (`agents/plan-lane-static.md`, `plan-lane-content.md`, `plan-lane-guardrail.md`, `plan-lane-g17.md`). The dispatch takes `subagent_type` from `lanes[i].agent` and sends one `NAME: value` line per name in `lanes[i].inputNames`, the value from `lanes[i].presetInputs` when present, otherwise from run-time context (`agent-dispatch-script-driven` guardrail); no `model` or `effort` is passed for a lane (the agent file sets both). A lane whose `agentPath` is null is not dispatched, and `merge-lanes` reports its missing result. The `guardrailsEvaluated` and `critiqueRan` markers are written after `merge-lanes` returns, never before every dispatched lane has returned. Lane dispatch failure / timeout / malformed output / missing result file surfaces as a blocking issue — never silently skipped. G17 (dimension-coverage) failure remains advisory per R31 dispatch-failure fallback.
- R54 (judge calibration): The content-coverage critique lane (owner of G18/G19/G20/G21) MUST receive the path to plan-format-reference.md and read it before judging those gates, evaluating concreteness / render / code-ref anchoring against its worked examples rather than the prose gate definitions alone. The Step 2 planner MUST read plan-format-reference.md and match its worked examples (read-then-match), not merely be pointed at it. The reference is read at runtime, never embedded in a dispatched prompt (prompt-cache stability). The calibration reference MUST also contain at least one negative exemplar — a labeled BAD → GOOD pair showing prose narrating a render-trigger surface (R46/G19) alongside its corrected render — so the lane has a negative anchor to pattern-match against, not positive exemplars alone.
- R36 (Step 5 multi-reviewer fan-out): Step 5 (CRITIQUE) per-iteration dispatch fans out to 2–3 lens reviewers IN PARALLEL in a SINGLE message when plan has ≥5 tasks. Lenses per KD3: (a) **architecture** → Buildability, Task descriptions, Decision documentation, Dependency accuracy; (b) **requirements** → Requirements coverage, Metadata completeness, Plan completeness, OpenSpec G16, Exploration provenance, Best-practice traceability; (c) **risk** → File paths, Verification strategy, Scope discipline, Guardrail compliance. Each lens is a plugin agent (`agents/plan-lens-architecture.md`, `plan-lens-requirements.md`, `plan-lens-risk.md`); `subagent_type` and the prompt inputs come from `lensReviewers[]` (P17) by the R35 rule, and `model`/`effort` are passed only when the entry's `dispatchModel`/`dispatchEffort` is non-null (R8); when `dispatchModel` is null (the `balanced` preset), the R8 author rule may add `model: opus`. Merge: Status = `Approved` iff ALL lenses approved, else `Issues Found`; Issues = union of blocking issues across lenses (dedup by `(taskRef, message-normalized-prefix)`); Recommendations = string-prefix dedup. Each lens returns one fenced JSON block `{ status, issues: [{ taskRef, message, severity, dimension, blocking }], recommendations, traceability }`; the skill writes it to `<critiqueDir>/iter-<k>/lens-<lens>.json` (P22) and `plan.js merge-lanes --lenses` (R67) applies this merge. Iteration counter counts iterations, not reviewer dispatches; max 3 iterations preserved (R8). Model strategy: R8. Plans <5 tasks: one reviewer, `reviewerDispatch` (P25, agent `agents/plan-reviewer.md`, lens `all`), dispatched by the same rule.
- R-c1 (Step 5 await barrier): The Step 5 Plan Review Loop multi-lens fan-out MUST NOT consolidate or advance on partial or zero lens returns. It MUST collect exactly N lens results (N = lenses dispatched) before improving the plan, mirroring the R56/R-orchestrator-await barrier used by the orchestrator agents. The defect this closes: counting completed fan-out dispatches instead of returned lenses, which lets consolidation proceed even when a dispatch returns fewer lenses than requested.

## Gates

- G1: Requirements coverage — every requirement has at least one task. When `openspecContext.requirements[]` is present (R38), G1 is inventory-anchored: the static-structural lane evaluates coverage against the structured `reqId` entries rather than free-form spec text.
- G2: No orphan tasks — every task traces back to a requirement
- G3: Dependency integrity — no circular deps; every named dependency exists (PF4 via validate-plan-format.js)
- G4: File conflict potential — two tasks modifying the same file are in dependency order (PF12 via validate-plan-format.js)
- G5: Context sufficiency — each task description is self-contained for agent dispatch
- G6: Classification accuracy — complexity/risk assignments match heuristics
- G7: No scope creep — no tasks beyond stated requirements
- G8: Verification completeness — every task has at least one verification method
- G9: Decomposition balance — no task touches >5 files; no plan with >80% Trivial tasks
- G10: File existence — every "Modify:" path exists in the codebase (PF13 via validate-plan-format.js --root)
- G11: OpenSpec requirements coverage — every ADDED/MODIFIED delta spec requirement has at least one task (when openspecContext available). When `openspecContext.requirements[]` is present (R38), G11 lane evaluation is inventory-anchored: the lane cites specific `reqId` entries from the inventory rather than relying on LLM opinion of delta-spec text. When the inventory is null (CLI absent), G11 falls back to the existing delta-spec text scan behavior.
- G12: Dependency target existence — every "Depends on: Task N" references a task that exists (PF4 via validate-plan-format.js)
- G13: Self-containment test — the most complex task can be implemented from its Files + Contract + Acceptance criteria (+ optional Notes) + Key Decisions alone
- G14: Guardrail compliance — each guardrail evaluated against the plan; error-severity failures are blocking, warning-severity are advisory. G14 is owned by the guardrail-compliance lane in the Step 3 fan-out (R35); it produces the `## Guardrail Compliance` payload Step 4 writes.
- G15: Brief citation coverage — when `explorePack.manifestPath` was non-null AND the orchestrator produced a brief, every Standard/Complex task cites ≥1 `F-<DIM>-<n>` finding ID OR is marked "out-of-scope addition" with rationale. Trivial tasks are exempt. Severity: error when brief was produced; not applicable when fallback path ran.
- G16: OpenSpec tasks.md coverage — when `fromOpenspecDirect` is true: every entry in `openspecContext.tasks[]` is either (a) referenced by ≥1 plan task's `openspec-task.ref`, or (b) listed in `## Out-of-scope OpenSpec tasks`. Error severity (blocking).
- G17: Dimension Coverage — when G17 subagent dispatched: emit proposals per R31 criteria with R31 suppression and ranking rules. Severity: advisory (non-blocking).
- G18: Settlement / contract concreteness — every artifact-touching task carries a `Contract:` block whose decided shape is concrete for the task's plan type (type derived from `Files:` paths); flag any task that leaves the shape unsettled (absent Contract or a restatement of 'update X to do Y'). Error-severity; owned by the content-coverage lane. Backed by deterministic presence floor PF7 (validate-plan-format.js, default check set); LLM G18 judges concreteness above the floor.
- G19: Render-don't-narrate — for EACH render-trigger surface (R46 catalog items 1–8) a
  task touches, flags that surface if its shape is narrated in prose rather than
  rendered as a concrete artifact; a render for one surface does NOT excuse prose for
  another surface in the same task. Trivial docs/rename tasks are not flagged. Also
  flags any Contract that includes more than one rendered example per distinct
  contract shape (per R49 cap — one elided example per unique method+path for REST,
  or flag+type for CLI). Error-severity; owned by the content-coverage lane. LLM-only
  (semantic — render-trigger detection); hardened by prose. No deterministic floor (KD2).
  Exemptions driven by template metadata: when the active template (R61) marks a surface
  as render-exempt, G19 skips that surface.
- G20: Notes rationale-only — flags a `Notes:` block that restates the task's
  Contract/acceptance instead of carrying only rationale. Error-severity; owned by the
  content-coverage lane. Exemptions driven by template metadata: when the active

Additive: preserves R8, R35, R36, R42 — no gate definition changes.

### Verification Scorecard (Gates A/B)

Note: Gate A runs at Step 1 (pre-decomposition); Gate B runs at Step 5 (post-lens-merge).

Gates A and B apply the per-check severity model from opsx:verify verbatim (CRITICAL / WARNING / SUGGESTION), not the per-dimension paraphrase. Severity is assigned per individual finding, not per dimension:

- Incomplete `tasks.md` checkbox or requirement appearing unimplemented → **CRITICAL**
- Implementation diverges from a requirement or scenario uncovered → **WARNING**
- Design decision not followed or code-pattern deviation → **SUGGESTION**
- When uncertain, prefer SUGGESTION > WARNING > CRITICAL (per opsx:verify heuristic)

Gate A (intake audit, R39) runs before decomposition when `openspecContext.requirements` is present. Gate B (plan audit, R40) runs at Step 5 and produces the `## Verification Scorecard` section. Verdict labels are verbatim: any CRITICAL → *"…Fix before archiving."*; warnings only → *"…Ready for archive (with noted improvements)."*; clean → *"All checks passed. Ready for archive."* Both gates degrade gracefully when artifacts are missing (R43).

Gate B (plan audit, R40): `## Verification Scorecard` section presence enforced deterministically by PF9 (validate-plan-format.js, `--final`); LLM Gate B judges content quality above the floor.

### CI validation contract

Deterministic checks performed by `plugins/sdlc-utilities/scripts/ci/validate-plan-format.js`. These run outside the LLM gate pipeline — pass/fail is structural, not inferred.

- PF1: Header fields present (`Goal`, `Architecture`, `Source`, `Verification`)
- PF2: Task numbering contiguous from 0 or 1
- PF3: Required metadata present per task (`Complexity`, `Risk`, `Depends on`, `Verify`)
- PF4: Dependency references valid (no cycles, all targets exist); the result carries `details: [{ taskRef, message, gateId }]` — `gateId` `G12` for a nonexistent target, `G3` for a cycle (taskRef = the first task of the cycle)
- PF5: Task body valid (`Acceptance criteria` present with ≥1 checkbox; optional `Notes` block capped at ≤5 non-blank lines)
- PF6: `## Deviations & assumptions` section present at top of plan (implements R47 deterministic enforcement — not an LLM gate). Template-driven exemption: enforced only when the active template (R61) requires this section; a project override that omits it from its heading list exempts this check, leaving PF10 as the sole enforcement path for that project.
- PF7: Contract presence — every artifact-touching task (≥1 `Create:`/`Modify:`/`Test:` Files entry) carries a `**Contract:**` block (implements R53 deterministic floor for G18). Runs in the default check set.
- PF8: reserved — intentionally unallocated. A deterministic floor for G21 (self-contained code refs) was considered and dropped: distinguishing a change-site `file:line` from a precedent/context ref is semantic, so a PF8 proxy would mis-fire and block valid plans at the Step 6.6 gate (the same objection that keeps G19 LLM-only). G21 stays the LLM ceiling. The number is preserved to keep PF references stable.
- PF9: Scorecard presence — `## Verification Scorecard` section present (implements R53 deterministic floor for Gate B). Runs only under `--final`; omitted for lightweight plans that skip Step 5. Template-driven exemption: enforced only when the active template (R61) requires this section; a project override that omits it from its heading list exempts this check, leaving PF10 as the sole enforcement path for that project.
- PF10: Template-driven section presence — under `--final`, reads the active template (project `.sdlc/plan-template.md` when present, shipped default `plan-template-default.md` otherwise per R61), extracts required section headers (lines matching `## <heading>`), and checks each is present in the plan. Replaces hardcoded per-section checks for template-declared sections (R57-R60, R47, R40/R44). Runs only under `--final`; omitted for lightweight plans that skip Step 5.
- PF11: `**Commit:**` header field — when the plan header (the lines before the first `---`, `## ` or `### ` line, R66) carries a line starting `**Commit:**`, it is the only such line there and is exactly `` **Commit:** `<subject>` `` with optional trailing whitespace; `<subject>` is 1–72 characters, holds no `"`, backtick, `$` or `\`, and matches `commit.subjectPattern` from the project config (`--project-root`) when one is set. A plan without the field passes; `**Commit:**` lines below the header are not read. Runs in the default check set (lightweight and full plans).
- PF12: Shared Modify paths in dependency order — for every path that two tasks list as `Modify:` (Files entries of the task, before the next `## ` heading), one of the two tasks reaches the other through `Depends on` links, directly or transitively. A failure carries `details: [{ taskRef: "Task j", message, gateId: "G4" }]` (Task j is the later task). Runs in the default check set (deterministic owner of G4, R35).
- PF13: Modify path existence — only under `--root <dir>`: every `Modify:` path that holds no `*` exists under `<dir>`, the active worktree (distinct from `--project-root`, which locates the config). `Create:` and `Test:` paths are exempt. A `Modify:` path is exempt only when a task in the transitive closure of the checked task's `Depends on` lists the same path as `Create:`; a path created by a task that is not an ancestor still fails. A failure carries `details: [{ taskRef, message, gateId: "G10" }]`. Deterministic owner of G10 (R35); plan-sdlc Step 3 and Step 6.6 pass `--root`.

## Failure handling and resume

- E1: Spec/requirements not found → ask user to provide path or paste content
- E2: Codebase exploration fails (too large) → ask user to point to relevant directories
- E3: Plan reviewer loop exceeds 3 iterations → surface unresolved issues to user
- E4: Requirements are contradictory → flag specific contradictions, ask user to resolve
- E5: Output path fails → retry with different path; offer to print plan to screen
- E6: Prepare/orchestrator failure recovery — when `plan-explore.js` invocation fails or `sdlc:plan-explore-orchestrator` exits non-zero, plan-sdlc falls back to inline exploration. Append a one-line note to `.sdlc/learnings/log.md` with the error string (`## YYYY-MM-DD — plan-sdlc orchestrator skipped: <error>`). Brief absence is not a plan failure — the plan is still produced via the inline-exploration path.
- E7: Gate A CRITICAL finding — decomposition is blocked. Surface the findings to the user with two options: (1) fix the source change artifacts (proposal.md / delta specs / tasks.md) and re-run; (2) override and proceed anyway (records the override in `## Intake Audit Caveats`). No `--auto` override — CRITICAL findings require explicit user action.
- E8: Gate B CRITICAL verdict — re-enter the existing Step 6 IMPROVE loop with the scorecard findings injected as blocking issues. Bounded by the existing 3-iteration cap (R8). If CRITICAL findings persist after the cap, surface to user via the existing max-iterations escalation path (R19/R22 preserved).
- E9: Critique-script failure — a `validate-plan-format.js` exit 2 or a non-zero `plan.js merge-lanes` exit at Step 3 or Step 5 stops plan-sdlc: the skill removes `<critiqueDir>` (P22) and invokes `error-report-sdlc`. A non-zero `plan.js g17-prepare` exit does not stop the run (R31 prepare-failure fallback); a non-zero `plan.js diff-material` exit counts as a material change with `affectedLanes: ["*"]` (R64).
- R19: At Step 5 reviewer-loop max-iterations escalation and Step 4 error-severity guardrail blocker, the skill MUST present an opt-in menu option that dispatches `Skill(harden-sdlc)` with `--failure-text <full failure text>`, `--skill plan-sdlc`, `--step <step-id>`, `--operation <operation-name>`, and (when known) `--exit-code <N>`. Selection is user-initiated only — the skill MUST NOT auto-dispatch and MUST NOT write any hardening surface silently. Menu wording is canonical and identical across all caller skills (`plan-sdlc`, `execute-plan-sdlc`, `review-sdlc`, `commit-sdlc`) and is suppressed when `--auto` is set.
- R23 (Step 0 session-recovery default): When the designated plan file already has content at Step 0, the skill MUST restart and overwrite without prompting. The prior draft is discarded; the user retains full control by `cp`ing the file before invocation. Rationale: stale drafts are rarely worth resuming, deterministic behavior is required for `--auto`, and the alternative (prompting) is the very user touchpoint R22 forbids. Existing R20 plan-integrity markers (`skillInvoked`, `planFile`, `guardrailsEvaluated`, `critiqueRan`) are UNAFFECTED by this requirement — they continue to be written at the same sites regardless of whether the plan file existed before the run.
- R28 (Orchestrator-failure fallback): When `explorePack.error` is non-null OR the orchestrator returns non-zero, Step 1 falls back to inline exploration without the brief. Plan is still produced. Failure is logged to `.sdlc/learnings/log.md`.

## Invariants and constraints

- R15: Prepare script output is the single authoritative source for all contracted fields (P-fields) — script-provided values take unconditional precedence over skill-generated content, and all factual context (git state, config, flags, metadata) must originate from script output to ensure deterministic behavior
- C1: Must not write implementation code in the plan (code snippets for patterns are fine)
- C2: Must not mandate TDD for every task — match verification to task type
- C3: Must not invoke execute-plan-sdlc within the same turn as plan-sdlc
- C4: Must not create plans with fewer than 2 tasks
- C5: Must not skip the plan review loop (unless lightweight routing)
- C6: Must not use absolute file paths that only work on one machine
- C7: Must not put plans in `$TMPDIR` — plans must survive session boundaries
- C8: Must not ignore plan mode's designated file path when plan mode is active
- C9: Must not skip, bypass, or defer prepare script execution — the script must run and exit successfully before any skill phase begins
- C10: Must not override, reinterpret, or discard prepare script output — for every P-field, the script return value is authoritative and final; the skill must not substitute LLM-generated alternatives
- C11: Must not independently compute, infer, or fabricate values for any field the prepare script is contracted to provide — if the script fails or a field is absent, the skill must stop rather than fill in data
- C12: Must not re-derive data the prepare script already computes via shell commands, tool calls, or LLM inference — script output is the sole source for all factual context, preserving deterministic behavior

### Plan document invariants

- R4: Each task must touch 1-5 files; more than 5 files requires splitting
- R5: Per-task metadata format is mandatory: Complexity, Risk, Depends on, Verify, Files, Acceptance criteria
- R6: Key decisions documented where a reasonable implementer might differ without the rationale
- R7: Verification strategy matches task type: feature→TDD, config→build, docs→manual, integration→E2E
- R9: When OpenSpec context is available, map every ADDED/MODIFIED requirement from delta specs to at least one task
- R12: Plans with fewer than 2 tasks should not be created — just do the work directly
- R27 (Brief traceability): Step 2 cites brief finding IDs in task descriptions. Standard/Complex tasks each reference ≥1 `F-<DIM>-<n>` ID OR are explicitly marked "out-of-scope addition" with rationale. Trivial tasks are exempt. When web/hybrid dimensions ran, Key Decisions explicitly ADOPTS / REJECTS-with-rationale / marks NOT-APPLICABLE each web finding, citing its ID.
- R29 (`openspec-task` annotation requirement): When `--from-openspec <name>` is passed AND the change has a `tasks.md`, plan-sdlc MUST annotate every plan task derived from an OpenSpec task with an `openspec-task: { change, ref, line, title }` block. `ref` is a stable kebab-slug-plus-6-char-content-hash identifier of the OpenSpec task title. Plan tasks not derived from any OpenSpec task MUST omit the field. N:1 mapping (multiple plan tasks → same ref) is allowed and intentional.
- R30 (tasks.md coverage requirement): When R29 applies, every `- [ ]` line in source tasks.md MUST map to at least one plan task carrying the corresponding `openspec-task.ref`, OR be explicitly listed in a plan section titled `## Out-of-scope OpenSpec tasks` with a one-line rationale per entry. Uncovered tasks with no documented out-of-scope entry are a blocking critique failure (G16).
- R45 (Always-settle checklist + per-task `Contract:` block): Every plan MUST settle 10 items per task; each item maps to where it is satisfied in the plan format:
  1. **Scope** → the task's scope statement (`### Task N:` title + `**Files:**`).
  2. **Target artifacts** → `**Files:**` (Create/Modify/Test paths).
  3. **Deliverable contract** → a new per-task `**Contract:**` block (mandated below).
  4. **Decisions pinned** → `Contract.decisions` (the per-task decided choices, bound to this deliverable — distinct from ambient `## Key Decisions`).
  5. **Names / identifiers** → `Contract.names` (exact symbols, IDs, headings, fields the deliverable introduces or touches).
  6. **Source-of-truth / precedent** → `Contract.mirror` (the existing artifact the deliverable mirrors, with line anchors).
  7. **Dependencies** → `**Depends on:**`.
  8. **Acceptance** → `**Acceptance criteria:**`.
  9. **Verification method** → `**Verify:**` (existing field + G8; no new enum).
  10. **Cross-artifact consistency** → `Contract.sync` (the sibling artifacts that must stay byte-consistent with this deliverable).

  R45 mandates a per-task `**Contract:**` block on every artifact-touching task, carrying the **type-aware decided shape** — execution renders it verbatim and does not redesign. The shape is type-specific by the three contract columns:
  - **code column** — signatures / types / flags / error-cases / import-paths the change introduces.
  - **docs column** — template + section list + audience + cross-links.
  - **openspec column** (also spec) — requirement IDs ADD/MODIFY/REMOVE + delta text + numbering + downstream obligations.

  The task's plan type is derived from `**Files:**` paths (no explicit `kind:`/`type:` discriminator), and a mixed-artifact task is judged against its dominant artifact's column. Concreteness is judged by the content-coverage lane gate G18, not a regex check.

  The Contract block carries the four keys mapped above (`decisions`, `names`, `mirror`, `sync`) plus one optional `example:` key — a concrete input/output pair, used only when the shape's prose leaves a genuinely ambiguous boundary. `example:` is omitted whenever a render-trigger surface (R46) already applies, since the render itself serves as the example. `example:` is not counted as one of the 10 always-settle checklist items; it is a clarifying aid the planner adds at its discretion, not a required presence check.

- R46 (Render don't narrate): When a task has a concrete artifact — a
  payload, data shape, status mapping, call order, or end-state — the plan SHOWS it
  (fenced block / table / before→after diff); prose is for rationale only, never for content with
  an exact shape. Surface-conditional: render only the artifact(s) the task's surface
  touches (catalog items 1–8, documented in plan-format-reference.md). Capped: one
  illustrative, elided (`…`) example per distinct contract shape — never an exhaustive dump. Enforced
  by G19 (error, blocking). Additive: preserves R42.
- R47 (Deviations section): Every plan MUST carry a top-of-plan `## Deviations & assumptions` section (table columns: Item | asked | does | why). Presence is enforced deterministically (PF6), not by an LLM gate.
- R48 (Notes field): The per-task `Description:` field is renamed `Notes:`, demoted to OPTIONAL and rationale-only; the executable shape lives in `Files:` + `Contract:` + `Acceptance criteria:`. Flagged by G20 (blocking) when a `Notes:` block restates the task's Contract/acceptance instead of carrying only rationale; a `Notes:` block of ≤5 non-blank lines is enforced deterministically (PF5 in `validate-plan-format.js`).
- R49 (per-distinct-shape cap): One illustrative, elided (`…`) example per distinct contract shape (not per surface category). Enforced by G19 (error, blocking).
- R50 (Mermaid): Mermaid fenced blocks are allowed for flow / call-order / state surfaces; no MDX.
- R51 (self-contained code refs): A bare `file:line` change reference is forbidden; embed the surrounding lines (or the full function body) plus an inline `-`/`+` diff. Flagged by G21 (blocking). A `file:line` used as a pointer / `Contract.mirror` precedent anchor is exempt.
- R52 (de-dup rationale convention): One rationale per decision — convention / guidance only, not gated.
- R57 (Context section): Every plan MUST carry a `## Context` section, placed near the top, giving the problem/background and the key exploration or research findings that motivated the plan, in plain language. Presence is enforced deterministically by PF10 via the active template (R61).
- R58 (Final Shape section): Every plan MUST carry a `## Final Shape` section describing the end-state once all tasks are complete — what the deliverable looks like when done, not how it gets there. Presence is enforced deterministically by PF10 via the active template (R61).
- R59 (OpenSpec Appendix section): Every plan MUST carry an `## OpenSpec Appendix` section consolidating the OpenSpec requirement inventory (`openspecContext.requirements[]`, R38) and the delta-spec-to-task mapping, so a reviewer does not need to open OpenSpec files separately. The heading is present on every plan regardless of OpenSpec status; when no OpenSpec change is active, its body reads "Not applicable — no OpenSpec change" — this keeps PF10's header-presence check uniform across OpenSpec and non-OpenSpec plans. Presence is enforced deterministically by PF10 via the active template (R61).
- R60 (Contract Examples section): Every plan MUST carry a `## Contract Examples` section, placed near the top, showing one worked `**Contract:**` block per column type (code / docs / openspec) actually used by the plan's tasks, so a reviewer unfamiliar with the field can read task Contracts without cross-referencing plan-format-reference.md. This is a reviewer-facing legend, distinct from the per-task `**Contract:**` blocks mandated by R45. Presence is enforced deterministically by PF10 via the active template (R61).
- R62 (plain-language style): Plans must use short sentences, explain every technical term inline, structure goals as bullet lists rather than prose blobs, and write decisions a non-expert can follow. This is a writing-quality convention judged by the existing Step 5 lens reviewers (R36) alongside their other checks — no new gate is introduced, and it is not enforced deterministically.
- R66 (`**Commit:**` header field): A plan MAY carry one `` **Commit:** `<subject>` `` line in its header, meaning the lines before the first `---`, `## ` or `### ` line. `<subject>` is the exact subject of the single commit a ship run makes for this plan: one line, 1–72 characters, matching `commit.subjectPattern` when set, and containing no `"`, backtick, `$` or `\`. Nothing but optional trailing whitespace follows the closing backtick. `**Commit:**` lines below the header (per-task notes) are prose and are not read. plan-sdlc writes the field directly below the plan title when it can form a subject that meets these rules from the request, the branch and the prepare output's `commit` field (P23) (for example, the issue or tracking id a `commit.subjectPattern` requires); when it cannot, it leaves the field out and records why in `## Deviations & assumptions`. A plan author may edit the field. `validate-plan-format.js` checks it (PF11). Consumer: ship-sdlc R-plan-commit-subject.
