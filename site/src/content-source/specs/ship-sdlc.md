# ship-sdlc Specification

> End-to-end feature shipping pipeline: execute plan, commit, review, fix critical issues, version, and open a PR. Chains six sub-skills sequentially with conditional review-fix loop, state persistence, and resume support.

**User-invocable:** yes
**Prepare script:** `skill/ship.js`

## Inputs and flags

### Flags

- A1: `--auto` — run pipeline non-interactively; forwarded to sub-skills that support it (default: false)
- A2: `--steps <csv>` — comma-separated steps to run; valid: execute, commit, review, received-review, commit-fixes, version, verify-openspec, archive-openspec, pr, verify-pipeline, await-remote-review, learnings-commit. When passed, fully replaces the resolved step list (config `ship.steps[]` and built-in defaults are ignored). The single source of truth for pipeline composition is config `ship.steps[]`; CLI `--steps` is a one-shot override.
- A3: `--quality full|balanced|minimal` — execution quality (model tier) for execute-plan-sdlc. When it is passed, ship forwards it. When it is absent in an interactive run, ship asks for the tier in its main context (`execute_tier`, options full|balanced|minimal), stores the answer in the ledger's `flags.quality` and forwards it; ship never picks a tier itself. Under `--auto` nothing is asked and ship forwards no tier; execute-plan-sdlc resolves it per its A6 (`balanced` unless resumed) (default: not set).
- A4: `--bump patch|minor|major|<label>` — version bump type forwarded to version-sdlc; `<label>` is any pre-release label matching `^[a-z][a-z0-9]*$` (e.g., `rc`, `beta`, `alpha`, custom). A label-form value is forwarded verbatim to version-sdlc, where it is interpreted as `--bump patch --pre <label>` (default: from config, else `version.preRelease` (R63), else the plan's commit type (R96), else patch)
- A5: `--draft` — create PR as draft (default: from config or false)
- A6: `--dry-run` — display pipeline plan without executing (default: false)
- A7: `--resume` — resume pipeline from saved state file (default: false)
- A8 (workspace auto-detection): There is **no** workspace flag. Workspace is not user-selectable — it is derived (see R60). `--workspace`, `--branch`, and `--tree` are **removed flags**: passing any of them is a hard error ("removed: workspace is auto-detected"). The prepare script (`skill/ship.js`) computes a derived `workspace` value (`branch` or `continue`) from cwd + current branch and emits it at `flags.workspace`; SKILL.md consumes it from `flags.workspace` (not `context.workspace` — the `context` object has no `workspace` key), it is never prompted, and the SKILL.md prepare-invocation bash example MUST NOT contain any workspace flag.
- A9: `--init-config` — run interactive config wizard, no pipeline execution (default: false)
- A10: `--openspec-change <name>` — explicitly select the OpenSpec change to archive, overriding branch matching (default: null)
- A11: `--plan <path>` — explicit path to the active plan markdown, required whenever the `execute` step will run; resolved solely from this CLI flag with no config-driven or directory-scan fallback (R72, C19, R-PLANFILE). Forwarded to execute-plan-sdlc as `--plan <path>` (default: unset)
- A12: `--rebase auto|skip|prompt` — rebase strategy for ship's own `rebase` step (R9, R75) (default: `skip`)
- A13: `--tasks <ids>` — forwarded unchanged to execute-plan-sdlc as `--tasks <ids>` (execute A8); ship checks that the value holds only digits and commas (R76) (default: unset)
- A14: `--from-wave <n>` — forwarded unchanged to execute-plan-sdlc as `--from-wave <n>` (execute A9); ship checks that the value is an integer (R76) (default: unset)
- A15: `--no-tag` — forwarded to the version step as `--no-tag` (version A9) (R79) (default: false)
- A16: `--no-push` — forwarded to the version step as `--no-push` (R79) (default: false)
- A17: `--release-subject <text>` — forwarded to the version step as `--subject "<text>"` (version A10) (R79) (default: unset)
- A18: `--review-threshold critical|high|medium|low` — CLI > config `ship.reviewThreshold` > default `high` (R40) (default: from config or high)
- A19: `--review-rounds <n>` — integer 1–3; the number of review → received-review → commit-fixes rounds (R84) (default: 1)

- R15: `--dry-run` displays pipeline table and stops without executing. It writes no ship state: no init, no prune and no `claimSession`, so a ledger it resumes, explicitly or implicitly, keeps its bytes and its mtime (the prepare output file is still written).
  - Acceptance: exec cases in `tests/promptfoo/datasets/ship-prepare-exec.yaml` whose descriptions start with `ship-prepare (R15)`.
- R16: `--init-config` redirects to `/setup-sdlc`; runs interactive wizard if user insists
- R28: `--openspec-change <name>` flag explicitly selects the change to archive, overriding branch matching.
- R63: When `version.preRelease` is set in `.sdlc/config.json` AND the resolved ship `flags.bump` was NOT sourced from the CLI (`flagSources.bump !== 'cli'`), the version step invocation MUST forward `--bump <version.preRelease>` instead of `--bump <flags.bump>`. An explicit CLI `--bump` graduates out of the pre-release train (consistent with version-sdlc R16). The prepare output MUST record the override by setting `flagSources.bump` to `'config (version.preRelease)'`.
- R72: Explicit-only plan resolution. When the resolved step list (`steps[]`) contains `execute` and no plan was supplied — neither `--plan <path>` on the CLI nor, on an explicit `--resume` that finds a ledger, the ledger's recorded `flags.planFile` (R11) — `ship.js` prepare MUST hard-error before any step dispatch or state write (no directory scan, no mtime heuristic, no settings-file fallback — see R-PLANFILE, C19). When `--plan <path>` IS supplied, prepare MUST verify the path exists on disk and has a `.md` extension; either check failing is also a hard error under this requirement. Every rejection MUST be emitted as a structured `{id, message}` error object with one of three ids — `missingPlanFile` (no plan from `--plan` or a resumed ledger, and `execute` is in the pipeline), `planFileNotFound` (`--plan` path does not exist on disk), or `planFileNotMarkdown` (`--plan` path exists but is not a `.md` file) — where `message` states (1) what failed, (2) how to fix it (pass `--plan <path>` pointing at an existing plan markdown file), and (3) why the rule exists (removes the directory-scan/mtime heuristic that mis-selected a plan from another repository). The error object MUST also be mirrored to stderr. The check MUST fire at prepare time — strictly before any step is dispatched and before any state file is written. `ship-sdlc/SKILL.md` MUST surface the `{id, message}` verbatim to the user; it MUST NOT paraphrase, re-derive, or suppress it. When a ship ledger exists for the current branch and the run gives neither `--resume` nor `--plan`, nothing is restored from it: `missingPlanFile` fires as before, and its message also names the ledger, its recorded plan and the `--resume` command.
  - Acceptance: exec tests in `tests/promptfoo/datasets/ship-prepare-exec.yaml` — `ship prepare (R72): steps contains execute with no --plan hard-errors with structured {id,message} before any state write`, `ship prepare (R72): --plan path that does not exist on disk hard-errors`, `ship prepare (R72): --plan path with non-.md extension hard-errors`, `ship prepare (R72): error object is mirrored to stderr`, `ship prepare (R72): valid --plan resolves context.planFile and prepare proceeds normally`; behavioral coverage in `tests/promptfoo/datasets/ship-sdlc.yaml` asserts the orchestrating skill surfaces the `{id, message}` verbatim (citing R72).
- R-PLANFILE: The `ship.js` prepare script MUST resolve `context.planFile` (absolute path to the active plan markdown) SOLELY from an explicit CLI `--plan <path>` flag — no directory scan, no most-recently-touched-file heuristic, and no settings-derived lookup of any kind. When `steps[]` contains `execute` and no `--plan` was supplied, prepare MUST hard-error per R72 rather than resolve any fallback path (C19). On an explicit `--resume` that finds a ledger and gets no `--plan`, prepare uses the ledger's recorded `flags.planFile` (R11): that value was itself written from an explicit `--plan`, so it is an explicit source, and no directory scan or mtime rule is added. The resolved path MUST be emitted as `context.planFile` in the prepare-output JSON. The `ship-sdlc/SKILL.md` execute block MUST assign `PLAN_FILE` via a single Bash command from `context.planFile` — no LLM-side path inference is permitted. The `ship.js` execute-step args assembly MUST append `--plan "$PLAN_FILE"` to the dispatched execute-plan-sdlc invocation.
- R-plan-commit-subject: When `context.planFile` is set and the plan header carries a `**Commit:**` field (plan-sdlc R66), `skill/ship.js` forwards its subject to the `commit` step as `--subject "<subject>"` (commit-sdlc A7), placed before `--expected-branch` so R-expected-branch-injection's "ending with" acceptance holds. R66 excludes `"`, backtick, `$` and `\`, so the double-quoted value is safe in commit-sdlc's Step 0 shell line. A header `**Commit:**` line that breaks R66, or whose subject does not match `commit.subjectPattern`, is a prepare error `{ id: 'planCommitSubjectInvalid', message }`, mirrored to stderr, before any step runs. When the field is absent, the commit step gets no `--subject` (unchanged behaviour). A plan that exists but cannot be read is also a `planCommitSubjectInvalid` error, and every `--after` call that recomputes the steps, except the final `cleanup` call, reads the field with the same check, `commit.subjectPattern` included, so a field that has become unreadable or invalid stops that call with an error envelope before anything is recorded, and so does a project config `.sdlc/config.json` that cannot be read or parsed (the error names `.sdlc/config.json`). The plan header's optional `**Fix commit:**` field (plan-sdlc R68) is read by the same call with the same checks; its subject goes to the `commit-fixes` step as `--subject "<subject>"`, before `--expected-branch`, and a malformed field is the same `planCommitSubjectInvalid` error. Without the field, `commit-fixes` gets no `--subject` and the commit-orchestrator drafts the subject. The steps are recomputed from the frozen `planFile`, so the branch_prepare recompute (R-expected-branch-branch-derive) keeps the subject.
  - Acceptance: exec cases in `tests/promptfoo/datasets/ship-prepare-exec.yaml` — `ship-prepare (R-plan-commit-subject): header field forwards --subject to the commit step only` (commit args contain `--subject "<subject>"` before `--expected-branch`; commit-fixes args contain no `--subject`), `ship-prepare (R-plan-commit-subject): malformed header field hard-errors with planCommitSubjectInvalid`, and `ship-prepare (R-plan-commit-subject): plan without the field forwards no --subject`, `ship-fix-subject: (a)` (a `**Fix commit:**` field reaches commit-fixes only) and `ship-fix-subject: (b)` (a malformed field hard-errors).
- R75: Without `--rebase` and without `ship.rebase` in `.sdlc/local.json`, the rebase strategy is `skip`. `ship.rebase` maps `true` → `auto`, `false` → `skip` and `"prompt"` → `prompt`; the CLI `--rebase` wins over config. `skill/ship.js` records the source in `flags.sources.rebase` (`cli`, `config` or `default`).
  - Acceptance: the case `ship-prepare: BUILT_IN_DEFAULTS resolve to balanced steps (no version) when no config exists` resolves `"rebase": "skip"`; the `ship-prepare (R75)` cases resolve config `true` to `auto` with source `config`, and `--rebase auto` to `auto` with source `cli`; the `ship-prepare (R75)` default-ledger case records `flags.rebase: "skip"`; and `ship-step: (q) review_gate below-threshold findings …` records `rebase` in `progress.skipped` for `skip`.
- R76: Execute selection pass-through. `skill/ship.js` forwards `--tasks <ids>` (A13) and `--from-wave <n>` (A14) with their raw values, unchanged, in the `execute` step's `args` only, after `--quality`; no other step gets them. Ship checks only the form of the values: a `--tasks` value must hold digits and commas only (`^[0-9,]+$`, so no whitespace) and a `--from-wave` value must be an integer (`^[0-9]+$`); any other value, and a flag with no value (last argument, or followed by another `--` flag), is a prepare error that names the flag and the value. execute R43 still validates the ids and the wave number. The ledger's `flags` holds this run's values, because the step emitter builds `dispatch_execute`'s args from the ledger; every run replaces them with its own CLI values (absent when not given), so `--resume` never restores them (R11 restores only the plan and the steps). execute's state file keeps the selection across its own resume (execute R43). `dispatch_execute`'s task check and the failed-task listing keep reading the whole plan.
  - Acceptance: exec cases in `tests/promptfoo/datasets/ship-prepare-exec.yaml` whose descriptions start with `ship-prepare (R76)`.

### Derived inputs

- R60 (workspace auto-detection): Workspace is **not user-selectable** — it is **derived**, never prompted, never flagged. The derive is a pure function `deriveWorkspace({ inLinkedWorktree, currentBranch, defaultBranch })` (exported from `lib/git.js`, no I/O) returning exactly two outcomes:
  - **`branch`** — cwd is the **main** worktree AND HEAD is the **default** branch. ship-sdlc auto-creates a feature branch before dispatching execute. Lifecycle: (1) derive branch name from the plan title via `plugins/sdlc-utilities/scripts/lib/branch-name.js` driven by `workspace.branch` config (no hardcoded template/slug rules in SKILL.md); (2) `git checkout -b <name>` in ship's main shell (the command emitted by the `branch_prepare` step); (3) migrate the ship ledger (R37) from the OLD branch slug to the NEW name in `ship.js` during `--after branch_prepare`. After (2), cwd is the main worktree on the new feature branch, so execute-plan-sdlc's own derive yields `continue` — ship does NOT forward a `--branch` value (no value crosses the boundary).
  - **`continue`** — every other case: a linked (non-main) worktree (`inLinkedWorktree === true`), OR the main worktree already on a feature branch (`currentBranch !== defaultBranch`). ship-sdlc runs the pipeline **in place** on the current branch in the current cwd; no branch is created, no migration runs, version runs normally (tags are repo-global).

  `skill/ship.js` computes the derived `workspace` from already-available data (`detectWorktree`/`worktreeInfo.inLinkedWorktree`, `gitState.currentBranch`, `detectBaseBranch`/`defaultBranch`) and emits it at `flags.workspace` in the prepare output. SKILL.md MUST read the derived value from `flags.workspace` (the `context` object carries **no** `workspace` field); reading any other path is a defect. The default-branch check stays **advisory** (a preflight `warnings.push`, not a halt — `ship.js:882`): on the default branch in the main worktree, the derive returns `branch` and a feature branch is auto-created, so the warning never strands a run. Path-anchoring (`resolveMainWorktree`/`resolveMainWorktreeSafe`/`resolveSdlcRoot`) is **kept** — it anchors `.sdlc/` to the main worktree, which is what makes running inside a user's manual linked worktree correct.
  - Acceptance: "`deriveWorkspace` returns `branch` ONLY for main-worktree + default-branch, and `continue` for (a) any linked worktree and (b) feature-branch-in-main-worktree. Under a derived `branch` run from `main`, `git branch --show-current` returns the NEW branch in ship's main shell BEFORE execute is dispatched, and `state/ship.js read` after migration returns `data.branch === <newName>`. Under a derived `continue` run, no branch is created and no migration runs. The default-branch advisory is a warning, not a halt."

## State model

### Ship state file

- R10: State persistence after each step via `state/ship.js`; cleanup validates pipeline contract before deleting state; state preserved on validation failure
- R73: Session-scoped hook enforcement. Ship state MUST carry a `sessionId` field, stamped with the Claude Code session id whenever a session *claims* the pipeline — on `init` AND on `--resume` (a resumed pipeline re-stamps `sessionId` so the resuming session, not the original one, becomes the enforcing session). The three continuation-enforcement hooks (`pipeline-continue.js` R67, `stop-pipeline-continue.js` R68/R-stop-inprogress-mode-independent, `block-askuserquestion-auto.js` R71) MUST consume a single shared predicate `hookEnforcementAllowed(data, payload)` (`lib/state.js`) — a pure function taking the parsed state object and the hook's parsed stdin payload, returning `{allowed: boolean, reason: string}`, mirroring `pipelineAdvancing(data)`'s shape — as a scoping gate applied BEFORE their own `pipelineAdvancing`-driven logic. The predicate gates SOLELY on stdin `session_id` (from the hook's JSON stdin payload) equalling the state file's `sessionId`. Any missing value (stdin `session_id` absent, or state `sessionId` absent — e.g., a pre-R73 state file) or any mismatch MUST resolve to `false` (no enforcement) — the failure direction is explicit: fail OPEN to silence, never fail CLOSED to blocking, so a hook never enforces against a session it cannot positively confirm owns the pipeline. The predicate MUST NOT compare worktree paths (cwd, `resolveMainWorktree`, or any worktree identifier): linked worktrees legitimately share one main-worktree state directory, and a worktree-path comparison would incorrectly treat a second linked worktree working the same pipeline as a foreign session — worktree identity and session identity are orthogonal, and this gate speaks to the latter only. Omitting this negative clause would read as an oversight and invite re-adding a worktree comparison later; it is intentional and permanent. Ownership: a subagent shares its parent's session id (`CLAUDE_CODE_SESSION_ID` and the hook `session_id`), so a ship run inside a subagent is owned by the parent session, and the parent's hooks enforce it. A separate `claude -p` session stamps its own id, so the hooks of the session that launched it stay silent for its run. ship-sdlc must run at depth 0 (the main session or a headless session), because its review and execute steps dispatch two more agent layers.

- R-b1 (proceed-gate): `begin-step` MUST refuse (exit 1) to mark a step `in_progress` when any earlier step in `steps[]` is `pending`, `in_progress`, or `failed`. - R-advancing-predicate: A single shared pure predicate `pipelineAdvancing(data)` in `lib/state.js` is the sole source of truth for "the pipeline still has forward motion" — consumed VERBATIM by BOTH continuation hooks (R67, R68); neither hook may inline a duplicate predicate (`DRY`, `no-opposite-logical-vectors`). It returns `{ advancing, step, index }`, computed from the step list using the existing terminal-status convention (`status !== 'completed' && status !== 'skipped'`):
  - `paused`: when `data.paused` is set (R-pause), return `{ advancing: false, step: null, index: -1 }` before any step is examined
  - `inProgress = steps.find(s => s.status === 'in_progress')`
  - `failed = steps.some(s => s.status === 'failed')`
  - `pending = steps.find(s => s.status !== 'completed' && s.status !== 'skipped' && s.status !== 'failed')` (first step that is **not** terminal — `completed`/`skipped`/`failed` are all terminal here; `failed` MUST be excluded so it does not shadow a later `cleanup` step in the search)
  - `pendingIsCleanup` = the resolved `pending` step is the R38 terminal `cleanup` step (`pending && pending.name === 'cleanup'`)
  - `advancing = !!inProgress || (!!pending && (!failed || pendingIsCleanup))`

It is `false` when all steps are terminal (`completed`/`skipped`/`failed`), and `false` when a step `failed` and the only-remaining non-terminal work is something other than `cleanup` (or there is no remaining non-terminal step at all). The `failed`-exclusion in the `pending` search is load-bearing: without it, a `failed` step at index < cleanup would be returned as `pending`, making `pendingIsCleanup` false and stranding the R38 cleanup-after-failure path.

- R-pause: `state/ship.js pause [--reason <text>] [--state-file <path>]` sets `data.paused = {at, reason}`; `begin-step` (or `ship.js` when it emits a step) and `claimSession` (`--resume`) clear it (`begin-step` also removes the `.stop-cap-exhausted-<slug>.json` sidecar); `pipelineAdvancing` returns `advancing:false` while it is set, so both continuation hooks stay silent. ## Dispatch and routing

- R2: Sub-skills are dispatched per `steps[].dispatchMode` emitted by ship.js. Every sub-skill is Agent-dispatched (`dispatchMode: 'agent'`) including `execute-plan-sdlc`. Inline-Bash steps emit `dispatchMode: null`.

Consequently, on every fresh `workspace: branch` run, the `--expected-branch` value baked into `steps[commit|commit-fixes|version|pr].args`/`.invocation` by prepare is the pre-checkout branch (typically the default branch), not the feature branch — R-expected-branch-injection's acceptance criterion ("`context.expectedBranch` equals the current feature branch") is unsatisfiable at prepare time for this derive and must be corrected downstream. `skill/ship.js` MUST close this gap in its `--after branch_prepare` call: after `migrateBranchSlug` it recomputes the steps with `expectedBranch` set to the new branch, so every `--expected-branch <value>` in the emitted `steps[].args` and `steps[].invocation` (string-typed only — `cleanup`'s `invocation` is an object and MUST NOT be touched) carries the new branch. For a `workspace: continue` run, the prepare-output file is unmodified by this requirement.

## Gates

- G1: `gh` CLI authenticated when a selected step needs gh (R91)
- G2: Not on default branch — warn if on main/master (do not block)
- G3: Step values valid — all CLI `--steps` values are recognized step names (`VALID_STEPS` from `lib/ship-fields.js`)
- G4: At least one step will run — pipeline is not entirely skipped
- G5: Flag coherence — `--bump` without version step produces error (exit code 1, blocking). The `--bump` value space accepts `major|minor|patch` or any pre-release label matching `^[a-z][a-z0-9]*$`; values outside this set are rejected at parse time before the version step runs.
- G6: Pipeline contract — every `will_run` sub-skill step was dispatched via the Agent tool (`dispatchMode: 'agent'`); inline-Bash steps emit `dispatchMode: null`
- G6a: Pipeline completion gate — `state/ship.js cleanup` validates all steps are in terminal state (`completed`, `skipped`, or `failed`) before deleting the state file. Steps still `pending` or `in_progress` cause cleanup to refuse deletion and exit 1.
- G7: Staging gap filled — the R8 `stage_changes` commands ran between execute and commit
- G8: Rebase attempted when `--rebase auto` (or `prompt`) — rebase ran after commits, before version (when applicable)
- G9: Scope gate — `stage_*` stages only plan Files paths (R83); received-review's `--check-scope` passed (R82)
- R91: gh is required only by the steps that call it. `skill/ship.js::runValidation` treats `pr`, `verify-pipeline` and `await-remote-review` as gh steps. When one of them has `status: 'will_run'` in `steps[]`, an unauthenticated or expired gh, an account mismatch and a denied repo-access probe are `errors[]` entries, as before. When none will run, they are not errors: prepare adds one `warnings[]` line that starts `gh is not required by the selected steps` and names the first problem; `review` and `received-review` then cannot read or post to a pull request in this run. `context.ghAuth` still reports the probe result. A `gh auth status` call that timed out is reported as a timeout (`lib/git.js::probeGhAuth` sets `timedOut: true` and an `errorMessage` that starts `gh auth status timed out`), never as "Not logged in".
  - Acceptance: exec cases `ship-prepare: gh-gating (a)` and `(b)` in `tests/promptfoo/datasets/ship-prepare-exec.yaml`; `git-lib: probeGhAuth` in `tests/promptfoo/datasets/git-lib-exec.yaml`.

- R3: Pipeline plan is a binding contract: steps with `status: "will_run"` must execute; LLM cannot override
- R5: Skip set provenance tracked via `skipSource`: `cli`, `config`, `auto`, `condition`, `none`; fabrication guard blocks (error, exit code 1) on `default` source
- R-post-version-ancestry: After the version step completes and `NEW_TAG` is known, ship-sdlc MUST verify that the new tag is an ancestor of the feature branch via `scripts/util/verify-tag-ancestry.js --tag <NEW_TAG> --branch <EXECUTE_BRANCH> --remote origin`. On non-zero exit (tag is NOT an ancestor), ship-sdlc MUST abort the pipeline with the error: "Tag `<tag>` is not an ancestor of branch `<branch>`. The release commit landed on a different branch. Delete the tag (`git push origin :refs/tags/<tag>`) and re-run version step on the correct branch." This gate is a no-op when `NEW_TAG` is unset (version step was not in `steps[]`). The check MUST be performed before dispatching the `pr` step; it is the only safeguard against tags silently landing on orphaned commits.
  - Acceptance: when `verify-tag-ancestry.js` exits non-zero for a given tag/branch pair, ship-sdlc halts with the documented error message containing both the tag name and the branch name, plus the `git push origin :refs/tags/<tag>` remediation command; when `NEW_TAG` is unset the block is a no-op and the pipeline continues normally.

- R-INVARIANT-COMPLETENESS: After `execute-plan-sdlc` returns and before ship-sdlc marks the execute step complete, ship-sdlc MUST run `state/execute.js verify-completeness`, within the Scope below, as a blocking invariant check. If the script exits non-zero (exit 65 = missing task IDs; exit 2 = `plannedTaskIds` absent from state or script not found), ship-sdlc MUST mark the execute step `failed`, halt the pipeline, and NOT advance to commit or any subsequent step. Exit 65 produces a structured JSON error on stderr: `{missingIds, totalPlanned, totalAccounted}`; exit 2 indicates a structural state problem (state written before `plannedTaskIds` was recorded, or corrupted init). Note: state files that lack `plannedTaskIds` will trigger exit 2 on any `--resume` attempt; users must start a fresh run rather than resuming from such state files. Scope: the check covers an execute run that ship dispatched and that returned to ship, when an execute state file for the branch exists at that point (a corrupt file counts as existing). When none exists — execute-plan-sdlc's R14 cleanup, which deletes the file only after the same check passed, or the R5 small-plan path, which never writes one — ship-sdlc records the execute step completed without running the check and adds `completenessGate: "no-execute-state"` to that history entry's data. After a pending-question stop, when the user answers `finished` at `execute_handoff`, ship runs the check if an execute state file exists (halting on any non-zero exit); if none exists, ship records execute completed with `source: "user-attested"` in the ledger history and names it in the summary.
  - Acceptance: when `state/execute.js verify-completeness` exits 65, ship-sdlc's pipeline halts with the execute step in `failed` status and does NOT dispatch commit-sdlc; when the script exits 2 (plannedTaskIds missing), ship-sdlc halts with exit 2 before advancing; when the script cannot be located, ship-sdlc exits 2 with the error "Cannot locate execute.js — completeness gate cannot run"; when all tasks are accounted the pipeline advances normally. When `execute-plan-sdlc` returns success and no execute state file exists for the branch, the execute step is recorded completed with `completenessGate: "no-execute-state"` and the pipeline advances to `stage_changes`.

On any failure `errors[]` carries `config-version: <role>: <message>` and prepare exits 1.

- P11: `warnings` (string[]) — non-blocking notices shown before the pipeline runs, including the cap-exhausted stall notice (R-cap-recovery)
- P12: `flags` gains `noTag`, `noPush`, `releaseSubject`, `reviewRounds`, with `sources` entries

## Failure handling and resume

- E1: Sub-skill fails (script crash) → stop pipeline, save state for `--resume`; sub-skill handles its own error reporting
- E2: `gh auth status` fails and a gh step will run → stop at validation, tell the user to `gh auth login` (R91); a timeout is named as a timeout
- E3: `git add` fails → stop pipeline, show error
- E4: Network error (gh API) → auto-retry with exponential backoff (the attempt count is a tuning value); if exhausted, save state
- E5: State file write fails → warn and continue (best-effort)
- E6: Resume state file corrupt → warn, start fresh
- E7: Review verdict unparseable → treat as APPROVED WITH NOTES, warn user
- E8: Rebase conflict → abort rebase; auto mode stops, interactive offers pause/skip/merge options
- E9: Sub-skill times out → stop pipeline, save state
- E10: `releaseSubjectInvalid`, `rerunGuard`, `stageOutsideFiles` and a received-review scope failure end the run with an error or a pending question; nothing is staged or dispatched after them

- R-config-failure-mode: A migration failure halts the pipeline before step 1 — no partial pipeline runs. The prepare output is the single point of refusal: SKILL.md gates Step 4 (DO) on `errors.length === 0` from the prepare output. If a previous run partially migrated and the lock file (`.sdlc/.migration.lock`) is stale, the prepare surfaces a `ConfigMigrationLocked` error with PID guidance; the user is responsible for removing the lock manually after confirming no other migration is in flight.

- R48: `verify-pipeline` timeout MUST produce a warning log; pipeline MUST exit 0 (warning, not error) and continue to `await-remote-review`.
- R49: `--resume` after `verify-pipeline` exhaustion (timeout, abort, or cap) MUST NOT re-poll; tracked via state-file marker `verifyPipelineExhausted: true`.
- R54: `await-remote-review` timeout MUST produce a warning log; pipeline MUST exit 0 (warning, not error).
- R55: `--resume` after `await-remote-review` exhaustion MUST NOT re-poll; tracked via state-file marker `awaitRemoteReviewExhausted: true`.
- R64: When `/ship-sdlc` is invoked while plan mode is active, the prepare script (invoked from SKILL.md Step 0 with `--plan-mode-blocked`) MUST resolve all CLI/config flags as usual, compute the canonical `steps[]` array, and persist an init state file at `<stateDir>/ship-<branchSlug>-<timestamp>.json` via `lib/state.js initState` with every step in `pending` status and the resolved `flags` snapshot (including `bump`, `steps`, `preset`, etc.). The output JSON MUST include `flags.planModeBlocked: true` and `stateFile: <path>`. On the user's next `/ship-sdlc` invocation (after exiting plan mode), the existing implicit-resume mechanism (`detectResumeState` → `flags.implicitResume`) picks up the state file and resumes from the first pending step with the originally-resolved flags. When `--plan <path>` is given, prepare first runs the plan check of R-implicit-resume against the branch's ledgers: if an unfinished ledger of the branch recorded a different plan, it emits the same `resumePlanMismatch` error, mirrored to stderr, and writes no state — no init and no prune. Without `--plan`, prepare refuses the same way when any unfinished ledger of the branch recorded a `planFile`: the `resumePlanMismatch` message says "(no --plan given)" and names that ledger, its plan and the ways forward (`--resume`, `--plan <that plan>`, or the user's own cleanup with ship's verbs). Plan mode never prunes an unfinished ledger of the branch (owner Q22a). After that plan check, prepare reads every same-branch ledger file, parseable or not; a missing state directory means there is none. A ledger is open when it is unfinished or cannot be parsed. When exactly one ledger is open and it is plan mode's own ledger (its `flags` has no `planFile` key and has `planModeBlocked: true`) or a ledger of the same plan (`--plan` and its `flags.planFile` resolve to the same file, or `--plan` is absent and the ledger's `flags.planFile` is `null`), prepare adopts it: no init, no prune, no write; the output keeps its shape, with `stateFile` set to that ledger and `prunedOrphans: []`, so entering plan mode again is idempotent. Every other case with an open ledger stops with the same `resumePlanMismatch` error, mirrored to stderr, with no state write: an unfinished ledger whose `flags` has no `planFile` key and no `planModeBlocked: true`, a ledger file that cannot be parsed, or more than one open ledger. The message names every open ledger and the ways out: continue the run with `--resume`, or discard it with ship's own verbs (`state/ship.js skip` on each leftover step, then `state/ship.js cleanup-pipeline`); a file that cannot be parsed can only be removed by hand. Finished ledgers are replaced by the init as before (R-ship-init-prune).
  - Acceptance: exec cases in `tests/promptfoo/datasets/ship-prepare-exec.yaml` — `ship-prepare (R64): --plan-mode-blocked twice adopts its own ledger`, `… adopts an unfinished ledger of the same plan`, `… stops on an unfinished ledger that records no plan`, `… stops on a ledger file that cannot be parsed`, `… stops on two unfinished plan-mode ledgers`, `… replaces a finished ledger by init as before`.

## Invariants and constraints

- R19: Prepare script output is the single authoritative source for all contracted fields (P-fields) — script-provided values take unconditional precedence over skill-generated content, and all factual context (git state, config, flags, metadata) must originate from script output to ensure deterministic behavior
