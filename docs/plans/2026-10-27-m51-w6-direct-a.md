## Step composition

### Phases

1. PRE-FLIGHT — run `skill/setup.js` to detect current config state, legacy files, content status
   - **Script:** `skill/setup.js`
   - **Params:** none
   - **Output:** JSON → P1-P8 plus P-sections (project config state/sections/path, local config state, legacy file detection, content counts, detected version file/tag prefix/default branch, migration flag, openspec block, joined `sections[]`)
2. SELECTIVE-SECTION MENU — render rows from `prepare.sections[]`; user selects which sections to configure (legacy rows auto-selected and locked); empty selection exits without changes
3. MIGRATION (conditional) — consolidate legacy config files and migrate config schema
   - **Scripts:** `lib/config.js` → `consolidateLegacyFiles()` (renamed from `migrateConfig()`) for legacy file consolidation; then `scripts/skill/migrate-config.js` for schema migration via `lib/config-version.js::verifyAndMigrate`
   - **Params:** project root, legacy config paths
   - **Output:** merged config written to `.sdlc/config.json` (was `.sdlc/config.json`); `schemaVersion` stamp applied; backup written per R-layout-6
4. DISPATCH LOOP — for each selected section, print a verbose header (purpose, files-modified, consumed-by, config-file, current-value) sourced from `prepare.sections[i]`, then dispatch the appropriate branch:
   - `delegatedTo: null` → generic field loop (one AskUserQuestion per `section.fields[]` entry, optionally gated by `section.confirmDetected`)
   - `delegatedTo: 'inline-commit-builder' | 'inline-pr-builder'` → conditional inline pattern builders for `commit` / `pr` sections
   - `delegatedTo: 'setup-<sub>'` → invoke the sub-flow document (review-dimensions, pr-template, plan-guardrails, execution-guardrails, openspec-block)
   - **Output:** config files written to `.sdlc/config.json` and `.sdlc/local.json` via `lib/config.js::writeProjectConfig`/`writeLocalConfig` (each write stamps `schemaVersion: 3`); content artifacts written by sub-flows
5. SUMMARY — display what was created, updated, or migrated
   - **Script:** `skill/setup.js` (re-run for G2 validation)
   - **Params:** none
   - **Output:** JSON → P-fields re-read to verify correctness of written config

### Requirements

- R1: 5-step workflow: Pre-flight → Status Report → Migration → Config Builder → Content Setup → Summary
- R3: Migration logic: detect legacy config files (version.json, ship-config.json, review.json), offer merge into unified config, optionally delete originals
- R4: Config builder walks through missing sections interactively: version, ship, jira, review, commit patterns, PR title patterns
- R7: Default flow walks every configurable field. For each field the user is presented `keep | change | unset` actions. The legacy "early exit when everything is configured" behavior is preserved as an opt-in via `--unset-only` (see R-walk-1 / R-walk-2). `--force` no longer gates re-prompting (default already re-prompts) but retains its semantic of skipping the per-field "keep" prompt and reconfirming all values.
- R10: Project scan phase runs before content sub-flows to collect signals (dependencies, framework, CI, DB, tests, etc.)
- R11: Version section requires `mode` field (required by schema): `"file"` when version file detected, `"tag"` when not. Optional fields include `versionFile`, `fileType`, `tagPrefix`, `changelog`, `changelogFile`, `ticketPrefix`, and `preRelease`. The `preRelease` field, when set, is a string matching `^[a-z][a-z0-9]*$` that supplies a default pre-release label to version-sdlc when the user runs `version-sdlc` without an explicit base bump or `--pre`. Empty / skipped answers omit the field; the schema (`schemas/sdlc-config.schema.json`) does not require it.
- R14: Scan phase (R10) MUST use the Glob tool for all file/directory existence checks. Bash MUST NOT be used with glob patterns — zsh errors on unmatched globs. Bash is permitted only for `git`, `gh`, and `which` commands.
- R15: Ship config field enumeration (Step 3b) is authoritative from prepare script output P7 (`shipFields`). The skill MUST iterate every entry in `shipFields` and dispatch one `AskUserQuestion` per field — it MUST NOT hand-enumerate the field list or short-circuit the loop. Entries where `skip: true` (set by the prepare script when a `when.stepInActiveSteps` gate is unsatisfied) MUST be skipped at prompt-time but MUST remain in the `shipFields` array (array order and length are stable so downstream order assertions hold). Ship config writes use answers collected in this loop plus defaults for any field the user explicitly deferred. The `shipFields` contract emits a `steps` multi-select field (canonical step list) and the resulting config write is persisted at top-level schema `version: 2`. The contract MUST NOT emit a `preset` field or a `skip` field — those are legacy CLI-only sugar handled at parse time, not config-level fields.
- R16: When `openspec/config.yaml` is detected during full-interactive setup (Step 4 content menu), prompt the user to apply managed-block enrichment (default: yes). Detection uses prepare script output field `openspecConfig.exists`.
- R17: Enrichment uses a string-delimited managed block (`# BEGIN MANAGED BY sdlc-utilities (vN)` … `# END MANAGED BY sdlc-utilities (vN)`) with a plugin-owned version marker. The block is appended, updated, or left unchanged by `scripts/util/openspec-enrich.js`.
- R18: Re-running setup on an already-enriched config at the current plugin version is a no-op (exit 0, action: `"unchanged"`)
- R19: Version mismatch between the in-file managed block and the plugin-shipped version triggers an `update` action (block text replaced in place)
- R22: Content outside the managed block is never modified. If the config file lacks a section where the block would naturally fit, the managed block is appended at end-of-file with a preceding blank line.
- R-menu-1: Step 1 renders a numbered list of `prepare.sections[]` rows directly in chat (one line per row, format: `<N>. [<state>] <label> — <purpose first sentence>`), then asks the user a single free-text question: `Reply with the numbers to configure (e.g. 1,3,5, all, not-set, or none) [default: <all|not-set>]`. The reply is parsed against the `prepare.menuInputContract` contract (accepted patterns: `all`, `not-set`, `none`/`cancel`, comma- or space-separated numbers, ranges like `1-3`, and mixed lists like `1-3,7,10`). SKILL.md MUST NOT use `AskUserQuestion` for Step 1 — the question is asked as plain chat output and the user's next message is the answer. Invalid input re-prompts with a one-line error citing the offending token. Locked legacy rows are always included regardless of reply. Every visible row, badge, and per-option description is sourced from `scripts/lib/setup-sections.js` — SKILL.md MUST NOT hardcode option labels.
- R-menu-2: Each menu row shows the section's state badge (`set` | `not-set` | `legacy`) computed from detection state (project config presence, local config, legacy file presence, `localIsV1`, openspec managed-block version).
- R-menu-3: Migration rows are auto-selected and locked when `needsMigration === true` AND the row's `state === 'legacy'`. Locked rows refuse uncheck and always proceed into Step 3.
- R-menu-4: Only sections present in the user's selection (from menu reply OR `--only <ids>`) enter the Step 3 dispatch loop. Unselected sections are not configured. A reply of `none` or `cancel` (or an empty parsed id set after locked-row inclusion) exits cleanly with a "no changes" summary; no config files are written.
- R-menu-5: Invalid menu input (tokens that are not a number, range, or known keyword) re-prompts up to 3 times with a one-line error citing the offending token. After 3 failed parse attempts, the skill exits with `No valid input after 3 attempts — no changes made.` and writes no config files.
- R-verbose-1: Each section sub-flow in Step 3 prints a verbose header sourced from `prepare.sections[i]` BEFORE any AskUserQuestion: a `Purpose:` line, a `Files modified:` line, a `Consumed by:` line, a `Config file:` line, and a `Current value:` line. For sections with non-empty `fields[]`, the header is followed by an `Options:` block listing every field's name, type, default, and description.
- R-verbose-2: All option copy (purpose, per-field description, default, options) comes from `scripts/lib/setup-sections.js` (single source of truth). SKILL.md MUST NOT duplicate or paraphrase that copy.
- R-walk-3: End-of-run diff preview MUST render before any config write. The preview uses `lib/config.js::computeConfigDiff(before, after)` over in-memory JSON snapshots and renders a markdown table of changed fields (`path | before | after`). When `changed.length === 0`, the preview is replaced with a "no changes — nothing to write" message and the write step is skipped. The user must confirm the diff before the write step proceeds (suppressed under `--auto`).
- R-pr-expected-account: The `pr` section collects `expectedAccount` (string, free-form GitHub login) with default = origin remote owner via `parseRemoteOwner(cwd)`. Empty default when no remote is configured. Validation accepts any non-empty string (no enum). The field is a real entry in `setup-sections.js` PR section `fields[]` — the standard menu walk surfaces it; `delegatedTo` for the rest of the PR sub-sections (titlePattern, labels) is unchanged.
- R-pr-template-scaffold: The PR-template sub-flow (`setup-pr-template`) MUST scaffold the canonical path `.sdlc/pr-template.md` (NOT the deprecated `.claude/pr-template.md`). This applies to: `skill/setup.js` detection probes, `lib/setup-sections.js` `purpose` and `filesModified` for the `pr-template` section, and the `setup-pr-template` sub-flow itself. The deprecated read-side fallback in `lib/pr-template.js` is independent (see `pr-sdlc.md` R-pr-template-path) — setup never writes to the deprecated location, but the resolver still reads from it during the deprecation window.
  - Acceptance: invoking `setup-sdlc --pr-template` writes the PR template to `<project>/.sdlc/pr-template.md`; `prepare.sections[]` row `id: "pr-template"` exposes `filesModified: [".sdlc/pr-template.md"]` and the `purpose` line names `.sdlc/pr-template.md`.
- R-guardrail-category: Every guardrail proposal emitted by `scripts/skill/guardrails.js::buildProposals` MUST carry a non-empty `category` field. The `buildProposals` function MUST include an internal assertion that throws with the offending id list if any proposal is emitted without a `category`. This ensures the setup-guardrails sub-flow can display `[category]` tags per proposal.
  - Acceptance: running `guardrails.js` against any fixture produces JSON where every entry in the proposals array has `category` set to a non-empty string; a fabricated entry missing `category` causes the script to throw with a descriptive error listing the offending id(s).
- R-guardrail-framework-proposals: When project signals include a detected framework (`svelte`, `astro`) or database type (`prisma`), `buildProposals` MUST emit framework-specific guardrail proposals in addition to the universal proposals. At minimum: (a) Svelte signal → proposal `island-only-interactivity` (category `framework`, severity `warning`); (b) Astro signal → proposal `astro-island-only` or the same `island-only-interactivity` id with astro-specific description (category `framework`, severity `warning`); (c) Prisma signal (`signals.dbType === 'prisma'`) → proposal `prisma-migration-required` (category `framework`, severity `error`). The `frameworkMap` in `guardrails.js` MUST include `astro` as a recognized framework key.
  - Acceptance: fixture with `"svelte"` in detected frameworks → `island-only-interactivity` appears in proposals with `category: "framework"`; fixture with `"astro"` → astro-specific island proposal appears; fixture with `"prisma"` as dbType → `prisma-migration-required` appears with `severity: "error"` and `category: "framework"`.
- R-guardrail-custom-prompt: The setup-guardrails sub-flow Step 2 (PRESENT) MUST use a two-stage selection flow: (Stage A) display standard catalog proposals with `[category]` tag per proposal and prompt `all / select <numbers> / cancel`; (Stage B) always-on `AskUserQuestion` "Add custom project-specific guardrails?" (yes/no) that runs after Stage A unless the user cancelled in Stage A. The existing single-prompt form (`all / select / custom / cancel`) is removed. The ID validation regex (`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`) is unchanged.
  - Acceptance: Step 2 no longer has `custom` as a selection option alongside `all/select/cancel`; Stage B fires unconditionally after any non-cancel Stage A outcome; cancelling Stage A skips Stage B entirely.
- R-pr-default-branch: The `pr` section in `lib/setup-sections.js` MUST include a `defaultBranch` field (string, default sourced from `detectBaseBranchSafe(process.cwd())`) in its `fields[]` array. `detectBaseBranchSafe` is a non-throwing variant of `lib/git.js::detectBaseBranch` that returns `'main'` on any error (including git not available). The field label is "Target branch for PRs". The `summarizePr` function MUST include `defaultBranch` in the section summary string. `setup.js`'s inline `git symbolic-ref` block (lines 134-139 at time of writing) MUST be replaced with a call to the same `detectBaseBranchSafe` helper to eliminate duplicated detection logic.
  - Acceptance: `setup-sections.js` `pr` section `fields[]` contains a `defaultBranch` entry; running `setup.js --section pr` in a repo where `git symbolic-ref refs/remotes/origin/HEAD` returns `develop` yields `pr.defaultBranch === 'develop'`; running against a repo with no remote yields `pr.defaultBranch === 'main'` without throwing; a second run against the same fixture produces the same value (idempotent).
- R-version-prerelease-compat: The `setup.js` prepare script MUST emit a static `preReleaseCompat: { [fileType]: { level: "compatible" | "partial" | "incompatible" | "unknown", message: string } }` map keyed by every supported `fileType` enum value (`package.json`, `cargo.toml`, `plugin.json`, `pyproject.toml`, `pubspec.yaml`, `version-file`). When the user supplies a non-empty `preRelease` value in Step 3.G AND `mode === 'file'`, SKILL.md MUST consult `prepare.preReleaseCompat[<chosen-fileType>].level` BEFORE writing the section. `compatible` writes silently. `partial` and `unknown` require an explicit yes/no confirmation showing `message`. `incompatible` blocks with a `clear` (omit `preRelease`) / `proceed` (write anyway, accepting risk) choice. The compatibility check is a pure lookup with no LLM-derived heuristics.
  - Acceptance: prepare output includes a `preReleaseCompat` key with one entry per supported `fileType`; setting `preRelease: "rc"` with `fileType: "pubspec.yaml"` in the interactive flow produces the `incompatible` prompt before any write; the `clear` choice omits `preRelease` from the written `.sdlc/config.json`; the `proceed` choice writes it verbatim.

- P-STEP-2: Script accepts `--after <step_id> --result-file <path> --state <state_file>` for subsequent invocations after the initial call
- P-STEP-3: State file is created on first invocation, updated after each step, and cleaned up when status is `"done"`
- P-TRANS-1: Step transition map — TBD (to be defined during script migration)

## Dispatch and routing

- R9: Content setup sub-flows: review dimensions (`setup-dimensions.md`), PR template (`setup-pr-template.md`), plan template (`setup-plan-template.md`), plan guardrails (`setup-guardrails.md`), execution guardrails (`setup-execution-guardrails.md`), PR labels (`setup-pr-labels.md`)
- R9a: PR labels sub-flow (`setup-pr-labels.md`) — section id `pr-labels`, configFile `.sdlc/config.json`, configPath `pr.labels`, `delegatedTo: 'setup-pr-labels'`. Writes a `pr.labels` block matching `schemas/sdlc-config.schema.json#$defs/prLabelsSection`: `mode: "off" | "rules" | "llm"`, optional `rules: { label, when }[]`. The sub-flow runs `gh label list` for the picker, presents an idempotency prompt (`keep`/`replace`/`append`) when the block already exists, and merges into the existing `pr` section without clobbering siblings (`titlePattern`, `allowedTypes`, etc.). The default state for projects that never run this sub-flow is "no `pr.labels` key" — `pr-sdlc` Step 2b interprets that as `mode = "off"`.
- R9b: Plan template sub-flow (`setup-plan-template.md`) — section id `plan-template`, `configFile: '<delegated>'`, `configPath: null`, `delegatedTo: 'setup-plan-template'`, `optional: true`. Copies the shipped `plugins/sdlc-utilities/skills/plan-sdlc/plan-template-default.md` to the project-owned override path `.sdlc/plan-template.md` (`filesModified: ['.sdlc/plan-template.md']`). Consumed by `plan-sdlc` (template resolution) and `validate-plan-format.js` (PF10 required-section check). Without this override, `/plan-sdlc` falls back to the shipped default template.
- R13: Content sub-flows (setup-dimensions, setup-pr-template, setup-guardrails) inherit the parent skill's permission mode. Sub-flows MUST NOT call ExitPlanMode, change permission settings, or exit any mode.

## Gates

- G1: Pre-flight passed — `skill/setup.js` exits successfully
- G2: Config validation — re-run `skill/setup.js` after writing config to verify correctness
- G3: No direct file writes — all config writes go through `lib/config.js` functions
- G4: Version mode present — version section always includes `mode` field. Optional `preRelease` field, if collected, must match `^[a-z][a-z0-9]*$` (re-prompt on syntactic failure) AND must pass the `R-version-prerelease-compat` cross-field check against `prepare.preReleaseCompat[<fileType>]` (block or confirm per level). Both gates run BEFORE the config write.
- G5: Migration consent — legacy files only deleted after explicit user confirmation
- G6: Outdated scripts reported — when `scriptVersions.outdatedCount > 0`, SKILL.md MUST surface a visible warning naming the outdated files and directing the user to run `/setup-sdlc --migrate` or `/version-sdlc --init`; outdated files must never be silently ignored

## Prepare script contract

- R12: Prepare script output is the single authoritative source for all contracted fields (P-fields) — script-provided values take unconditional precedence over skill-generated content, and all factual context (git state, config, flags, metadata) must originate from script output to ensure deterministic behavior
- R-SCRIPT-VERSIONS: setup-sdlc MUST verify that installed pipeline-script files (those managed by `scripts/util/scaffold-ci.js`) are at-or-above the version expected by the running plugin. The prepare script (`skill/setup.js`) MUST invoke `scripts/util/scaffold-ci.js --check-only` and merge its per-file `{action, installedVersion, currentVersion}` output into the prepare JSON under a new top-level `scriptVersions: [{file, action, installedVersion, currentVersion}, ...]` array, with a companion `scriptVersions.outdatedCount` summary. No auto-fix — setup surfaces state only; the user is directed to run `/setup-sdlc --migrate` or `/version-sdlc --init` to update. `pluginVersion` is self-read at module init in `setup.js` from the plugin's own `.claude-plugin/plugin.json` using a `__dirname` walk (project-agnostic). Behavior: emit one `{file, action, installedVersion, currentVersion}` row per managed CI file; `action` is one of `missing`, `outdated`, or `current`. (Mirrors the existing `scaffold-ci.js --check-only` integration in version-sdlc Step 7.5; only the wiring is new.)
- P1: `projectConfig` (object) — `{ exists, sections, misplaced, path }` state of `.sdlc/config.json` (read with legacy fallback to `.sdlc/config.json` per R-deprecation-1)
- P2: `localConfig` (object) — `{ exists, path }` state of `.sdlc/local.json`
- P3: `legacy` (object) — `{ version, ship, review, reviewLegacy, jira }` each with `{ exists, path }`
- P4: `content` (object) — `{ reviewDimensions: { count, path }, prTemplate: { exists, path }, jiraTemplates: { count, path } }`
- P5: `detected` (object) — `{ versionFile, fileType, tagPrefix, defaultBranch }` auto-detected project settings
- P6: `needsMigration` (boolean) — true when any legacy file exists, any misplaced section found, OR `.sdlc/local.json` has a v1 ship section (`localIsV1` is true)
- P6a: `localIsV1` (boolean) — true when `.sdlc/local.json` ship section has legacy `preset`/`skip` keys, or lacks a top-level `version: 2` stamp
- P7: `shipFields` (array) — authoritative list of interactive ship-config fields sourced from `scripts/lib/ship-fields.js`. Each entry: `{ name, label, type, options, default, description, when?, skip }`. `name` is the local-config key; `options` is an array of valid values; `default` is the value applied if the user accepts the default answer. Optional `when: { stepInActiveSteps: <ship-step-name> }` declares a gate: the prepare script evaluates it against the `steps[]` selection and sets `skip: true` when the referenced step is absent, `skip: false` otherwise. Entries without `when` always have `skip: false`. The array order and length are always stable — skipped entries remain in the array; they are only excluded from prompting (see R15).
- P8: `openspecConfig` (object) — `{ exists: boolean, path: string, managedBlockVersion: number|null }` state of `openspec/config.yaml` and its managed block
- P-sections: `sections` (array) — joined view of `SETUP_SECTIONS` (manifest) × `detect()` state. Drives the Step 1 selective menu and the Step 3 verbose dispatch loop. Each row has shape:
  - `id` (string) — canonical section id (used by `--only`); one of `version`, `ship`, `jira`, `review`, `commit`, `pr`, `pr-labels`, `review-dimensions`, `pr-template`, `plan-template`, `plan-guardrails`, `execution-guardrails`, `openspec-block`
  - `label` (string) — human-readable section name
  - `state` (string) — `'set'` (configured) | `'not-set'` (no config) | `'legacy'` (legacy file present, `localIsV1`, or managed-block-version below current)
  - `summary` (string) — one-line summary of the current configuration (empty for `not-set`)
  - `locked` (boolean) — `true` when `needsMigration === true` and `state === 'legacy'`; locked rows are auto-selected in the menu and cannot be unchecked
  - `purpose` (string) — one-paragraph runtime explanation of what this section does
  - `configFile` (string) — `.sdlc/config.json` | `.sdlc/local.json` | `<delegated>` | `openspec/config.yaml` (legacy `.sdlc/config.json` may appear for legacy-detection rows during the deprecation window)
  - `configPath` (string|null) — dot-path within `configFile`, or `null` for delegated/content sections
  - `consumedBy` (string[]) — skill ids that read this section at runtime
  - `filesModified` (string[]) — workspace artifacts created or touched
  - `optional` (boolean) — `true` if the section is safe to leave unset
  - `delegatedTo` (string|null) — sub-skill id (`setup-dimensions`, `setup-pr-template`, `setup-plan-template`, `setup-guardrails`, `setup-execution-guardrails`, `setup-pr-labels`, `setup-openspec`), inline-builder id (`inline-commit-builder`, `inline-pr-builder`), or `null` for generic field-loop sections
  - `confirmDetected` (boolean) — `true` when the dispatcher must ask `yes` / `customize` / `skip` BEFORE iterating fields (currently only `version`)
  - `fields` (array) — entries with shape `{ name, label, type, options, default, description, validate? }` matching the `SHIP_FIELDS` shape; empty for delegated and inline-builder sections
- P-preReleaseCompat — static map keyed by every supported `fileType`; values are `{ level, message }`. Map content is data-only (no detection-time inputs); SKILL.md cites the resolved level by name.
- P-menuInputContract — object describing the accepted free-text patterns for Step 1's numbered-list reply: `{ tokens: { all, notSet, none, cancel }, allowsNumbers: true, allowsRanges: true, separators: [',', ' '], defaultToken: 'all' | 'not-set' (resolved from flags.unsetOnly) }`. SKILL.md cites this object verbatim when constructing the prompt and when parsing the user's reply — no inline LLM-derived grammar.

## Failure handling and resume

- E1: `skill/setup.js` exit non-zero → display error, stop
- E2: Config write fails → warn user, offer to retry
- E3: Migration conflict (unified config and legacy both have same section) → unified wins; report conflict to user
- E4: `lib/config.js` not found → show installation error

## Invariants and constraints

- C1: Must not delete legacy files without explicit user confirmation via AskUserQuestion
- C2: Must not invoke removed standalone skills (`/review-init-sdlc`, `/pr-customize-sdlc`, `/guardrails-init-sdlc`) — use sub-flow documents instead
- C3: Must not modify Jira templates directly — delegate to `/jira-sdlc`
- C4: Must not write config files using Edit/Write tools directly — always use `lib/config.js` functions
- C5: Must not skip AskUserQuestion for any user interaction
- C6: Must not assume `mode` for version section — always ask or detect
- C7: Must not skip, bypass, or defer prepare script execution — the script must run and exit successfully before any skill phase begins
- C8: Must not override, reinterpret, or discard prepare script output — for every P-field, the script return value is authoritative and final; the skill must not substitute LLM-generated alternatives
- C9: Must not independently compute, infer, or fabricate values for any field the prepare script is contracted to provide — if the script fails or a field is absent, the skill must stop rather than fill in data
- C10: Must not re-derive data the prepare script already computes via shell commands, tool calls, or LLM inference — script output is the sole source for all factual context, preserving deterministic behavior
- C-projectroot: Scripts that use `process.cwd()` as the project root silently break when invoked from a sub-directory or a git worktree. All projectRoot resolutions in this skill's scripts MUST route through `resolveSdlcRoot()` (lib/config.js); `process.cwd()` is forbidden except in documented bootstrap entry points. Note: the CLI default upgrade path in `skill/setup.js` invoked by setup-sdlc is a documented bootstrap entry point exempt from this constraint.
  - Acceptance: `resolveSdlcRoot()` is called to establish `projectRoot` in `skill/setup.js` and `util/setup-init.js`; no bare `process.cwd()` usage contributes to any path resolved against the project root; invoking the script from a repo sub-directory yields the correct root.
