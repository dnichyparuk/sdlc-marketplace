## Context

**What problem does this change solve?**

- **W8.28 (spec part).** execute-plan-sdlc's archive gate (R38) re-reads an OpenSpec `tasks.md` with an inline `node -e` script. The model builds that script's path from a plan-derived change name inside a double-quoted shell string. A name like `a$(touch PWNED)` would run a command, and a name with `../` would read a file outside `openspec/changes/` (PR #39 review F3). The code fix is a new script subcommand, `openspec-step.js tasks --change <name>`, which checks the name and receives it only as an argv element (a separate process argument, never shell text). The repository rule is spec first, so this plan writes the spec text before the code plan changes the script.
- **W8.27.** Three plan-sdlc prompt files tell the model to dispatch subagents with `mode: bypassPermissions`, a permission mode that skips the user's permission prompts. The installed plugin made five real such dispatches in M5 wave 3. With no `mode` parameter, a subagent inherits the session's permission mode, as execute's dispatches have done since W5.3.

**What prompted this change now?**

- The owner placed both items in M5.1 wave 1b, before the fork is installed (rulings w2-preflight Q2 and w3-review F3). Arbiter ruling pr40 adds the `.`/`..` rejection for W8.28.

**What does success look like?**

- C1 is the first commit of the wave. P-5 prints `SAME` for both specs, and `validate-spec-shape.js` prints no stdout line.
- After C2, `grep -rn bypassPermissions plugins/sdlc-utilities` prints nothing. The new `plan-no-bypass` case and the existing `plan-prepare` cases pass, and `check-consistency.js` exits 0.

## Key Decisions

1. **The spec sentence goes in R38, and I13 names the subcommand.**
   - Choice: R38 gains two sentences. One names `openspec-step.js tasks --change <name>` as the source of the re-parse. The other is the item's validation sentence: the pattern, not `.` or `..`, exit 2 as a usage error, argv only.
   - Alternative: a new requirement id for the validation rule.
   - Why: the item says "ids unchanged", and R38 is the requirement that owns the re-parse.
2. **No new integration id (I14).**
   - Choice: the `tasks` entry is a second clause of I13, which already describes `openspec-step.js flip`.
   - Alternative: a new I14 line.
   - Why: a new id changes the P-5 id set, and the plan source demands `SAME`. Both clauses describe the same script, so one entry fits.
3. **The check script scans lines, not dispatch blocks.**
   - Choice: any line of any `*.md` under `plugins/sdlc-utilities/agents/` or `plugins/sdlc-utilities/skills/` that contains `bypassPermissions` is a hit.
   - Alternative: parse the dispatch blocks and look only at a `mode:` key.
   - Why: the item asks for exactly this scan (Change 2). It is simpler and stricter, and the three target lines are the only hits today. The scan excludes `docs/` and `site/`, because historical plans quote the old text.
4. **The new case sets no `project_root`.**
   - Choice: the case sets only `script_path`.
   - Alternative: copy the sentinel case, which sets a `project_root` fixture that the script ignores.
   - Why: the script finds the repo through `__dirname`. A fixture copy would only add a temp directory and a `setup.sh` run, and exec cases without `project_root` already exist.
5. **Behavioural case (D8): none.** W8.27 is text-only, and the item says "No behavioural run". The W8.28 part of D8 belongs to the feat plan (its KD7).

**Non-goals:**
- No change to any other dispatch parameter (`model`, `run_in_background`, `isolation`) in the three blocks.
- No change to `docs/specs/plan-sdlc.md`, which has no dispatch-mode text.
- No change to execute's I12 or to ship's step-table row (`:290`). The item's spec change names only R38, I13 and ship I13.
- No widening of W8.27 to other text. No other permission-mode instruction exists (pre-flight section 3).

**Failure audience:**
- If C1 is wrong, the feat plan implements a wrong contract. That affects anyone who runs execute-plan-sdlc on an OpenSpec-sourced plan.
- If C2 misses a line, plan-sdlc keeps asking for elevated subagent permissions after the fork install. Every planner session would be affected.
