# ship-sdlc Specification

> End-to-end feature shipping pipeline: execute plan, commit, review, fix critical issues, version, and open a PR. Chains six sub-skills sequentially with conditional review-fix loop, state persistence, and resume support.

**User-invocable:** yes
**Prepare script:** `skill/ship.js`

## Inputs and flags

### Flags

- A1: `--auto` — run pipeline non-interactively; forwarded to sub-skills that support it (default: false)
- A2: `--steps <csv>` — comma-separated steps to run; valid: execute, commit, review, received-review, commit-fixes, version, verify-openspec, archive-openspec, pr, verify-pipeline, await-remote-review, learnings-commit. When passed, fully replaces the resolved step list (config `ship.steps[]` and built-in defaults are ignored). The single source of truth for pipeline composition is config `ship.steps[]`; CLI `--steps` is a one-shot override.
- A3: `--quality full|balanced|minimal` — execution quality (model tier) for execute-plan-sdlc. When it is passed, ship forwards it. When it is absent in an interactive run, ship asks for the tier in its main context (`execute_tier`, options full|balanced|minimal), stores the answer in the ledger's `flags.quality` and forwards it; ship never picks a tier itself. Under `--auto` nothing is asked and `--quality` stays required (default: not set).
- A4: `--bump patch|minor|major|<label>` — version bump type forwarded to version-sdlc; `<label>` is any pre-release label matching `^[a-z][a-z0-9]*$` (e.g., `rc`, `beta`, `alpha`, custom). A label-form value is forwarded verbatim to version-sdlc, where it is interpreted as `--bump patch --pre <label>` (default: from config or patch)
- A5: `--draft` — create PR as draft (default: from config or false)
- A6: `--dry-run` — display pipeline plan without executing (default: false)
- A7: `--resume` — resume pipeline from saved state file (default: false)
- A8 (workspace auto-detection): There is **no** workspace flag. Workspace is not user-selectable — it is derived (see R60). `--workspace`, `--branch`, and `--tree` are **removed flags**: passing any of them is a hard error ("removed: workspace is auto-detected"). The prepare script (`skill/ship.js`) computes a derived `workspace` value (`branch` or `continue`) from cwd + current branch and emits it at `flags.workspace`; SKILL.md consumes it from `flags.workspace` (not `context.workspace` — the `context` object has no `workspace` key), it is never prompted, and the SKILL.md prepare-invocation bash example MUST NOT contain any workspace flag.
- A9: `--init-config` — run interactive config wizard, no pipeline execution (default: false)
- A10: `--openspec-change <name>` — explicitly select the OpenSpec change to archive, overriding branch matching (default: null)
- A11: `--plan <path>` — explicit path to the active plan markdown, required whenever the `execute` step will run; resolved solely from this CLI flag with no config-driven or directory-scan fallback (R72, C19, R-PLANFILE). Forwarded to execute-plan-sdlc as `--plan <path>` (default: unset)

- R15: `--dry-run` displays pipeline table and stops without executing
- R16: `--init-config` redirects to `/setup-sdlc`; runs interactive wizard if user insists
- R28: `--openspec-change <name>` flag explicitly selects the change to archive, overriding branch matching.
- R63: When `version.preRelease` is set in `.sdlc/config.json` AND the resolved ship `flags.bump` was NOT sourced from the CLI (`flagSources.bump !== 'cli'`), the version step invocation MUST forward `--bump <version.preRelease>` instead of `--bump <flags.bump>`. An explicit CLI `--bump` graduates out of the pre-release train (consistent with version-sdlc R16). The prepare output MUST record the override by setting `flagSources.bump` to `'config (version.preRelease)'`.
- R72: Explicit-only plan resolution. When the resolved step list (`steps[]`) contains `execute` and no `--plan <path>` was supplied on the CLI, `ship.js` prepare MUST hard-error before any step dispatch or state write (no directory scan, no mtime heuristic, no settings-file fallback — see R-PLANFILE, C19). When `--plan <path>` IS supplied, prepare MUST verify the path exists on disk and has a `.md` extension; either check failing is also a hard error under this requirement. Every rejection MUST be emitted as a structured `{id, message}` error object with one of three ids — `missingPlanFile` (no `--plan` supplied and `execute` is in the pipeline), `planFileNotFound` (`--plan` path does not exist on disk), or `planFileNotMarkdown` (`--plan` path exists but is not a `.md` file) — where `message` states (1) what failed, (2) how to fix it (pass `--plan <path>` pointing at an existing plan markdown file), and (3) why the rule exists (removes the directory-scan/mtime heuristic that mis-selected a plan from another repository). The error object MUST also be mirrored to stderr. The check MUST fire at prepare time — strictly before any step is dispatched and before any state file is written. `ship-sdlc/SKILL.md` MUST surface the `{id, message}` verbatim to the user; it MUST NOT paraphrase, re-derive, or suppress it.
  - Acceptance: exec tests in `tests/promptfoo/datasets/ship-prepare-exec.yaml` — `ship prepare (R72): steps contains execute with no --plan hard-errors with structured {id,message} before any state write`, `ship prepare (R72): --plan path that does not exist on disk hard-errors`, `ship prepare (R72): --plan path with non-.md extension hard-errors`, `ship prepare (R72): error object is mirrored to stderr`, `ship prepare (R72): valid --plan resolves context.planFile and prepare proceeds normally`; behavioral coverage in `tests/promptfoo/datasets/ship-sdlc.yaml` asserts the orchestrating skill surfaces the `{id, message}` verbatim (citing R72).
- R-PLANFILE: The `ship.js` prepare script MUST resolve `context.planFile` (absolute path to the active plan markdown) SOLELY from an explicit CLI `--plan <path>` flag — no directory scan, no most-recently-touched-file heuristic, and no settings-derived lookup of any kind. When `steps[]` contains `execute` and no `--plan` was supplied, prepare MUST hard-error per R72 rather than resolve any fallback path (C19). The resolved path MUST be emitted as `context.planFile` in the prepare-output JSON. The `ship-sdlc/SKILL.md` execute block MUST assign `PLAN_FILE` via a single Bash command from `context.planFile` — no LLM-side path inference is permitted. The `ship.js` execute-step args assembly MUST append `--plan "$PLAN_FILE"` to the dispatched execute-plan-sdlc invocation.

  - Acceptance: `schemas/sdlc-local.schema.json` declares top-level `version` with `const: 2`; new configs written via `writeLocalConfig`/`util/ship-init.js` include `version: 2` at the top level (not nested in `ship`).
- R32: `lib/config.js::readLocalConfig` MUST auto-migrate v1 → v2 on read. Migration steps: (a) expand legacy `ship.preset` to `steps[]` via `PRESET_TO_STEPS` (full/balanced/minimal and legacy A/B/C aliases); (b) subtract any legacy `ship.skip[]` members from the expanded steps; (c) delete `ship.preset` and `ship.skip` from the in-memory object; (d) set `ship.steps = <result>` and top-level `version: 2`; (e) persist the migrated config back atomically; (f) emit a single stderr deprecation notice on first migration. Migration MUST be idempotent — reading a v2 config does not rewrite or re-emit. The `migrateConfig` (--migrate) flow also triggers the v1→v2 ship migration.
  - Acceptance: passing `{$schema, ship:{preset:"balanced", skip:[]}}` (no version) to `readLocalConfig` returns `{version:2, ship:{steps:[execute,commit,review,archive-openspec,pr,learnings-commit], …}}` and rewrites disk; passing the migrated result back to `readLocalConfig` returns identical content with no disk write and no second notice.
- R33: The setup-sdlc questionnaire (`shipFields` from `lib/ship-fields.js`) MUST emit a `steps` field (multi-select; options enumerate the six canonical steps `execute, commit, review, version, archive-openspec, pr`; default = all six). It MUST NOT emit `preset` or `skip` fields. `util/ship-init.js` MUST consume `--steps <csv>` (validated against `VALID_STEPS`) and write a config whose top level carries `version: 2`. The `--preset` flag MUST be removed from `ship-init.js` and rejected with a clear migration-pointer error if passed.

- R34: When no ship config exists and no `--steps` flag is passed, `BUILT_IN_DEFAULTS.steps` in `ship-fields.js` MUST equal `['execute','commit','review','archive-openspec','pr','learnings-commit']` (excludes the `version` step). The resolved `flags.steps` mirrors that array. ### Derived inputs

- R60 (workspace auto-detection): Workspace is **not user-selectable** — it is **derived**, never prompted, never flagged. The derive is a pure function `deriveWorkspace({ inLinkedWorktree, currentBranch, defaultBranch })` (exported from `lib/git.js`, no I/O) returning exactly two outcomes:
  - **`branch`** — cwd is the **main** worktree AND HEAD is the **default** branch. ship-sdlc auto-creates a feature branch before dispatching execute. Lifecycle: (1) derive branch name from the plan title via `plugins/sdlc-utilities/scripts/lib/branch-name.js` driven by `workspace.branch` config (no hardcoded template/slug rules in SKILL.md); (2) `git checkout -b <name>` in ship's main shell (the command emitted by the `branch_prepare` step); (3) migrate the ship ledger (R37) from the OLD branch slug to the NEW name in `ship.js` during `--after branch_prepare`. After (2), cwd is the main worktree on the new feature branch, so execute-plan-sdlc's own derive yields `continue` — ship does NOT forward a `--branch` value (no value crosses the boundary).
  - **`continue`** — every other case: a linked (non-main) worktree (`inLinkedWorktree === true`), OR the main worktree already on a feature branch (`currentBranch !== defaultBranch`). ship-sdlc runs the pipeline **in place** on the current branch in the current cwd; no branch is created, no migration runs, version runs normally (tags are repo-global).

  `skill/ship.js` computes the derived `workspace` from already-available data (`detectWorktree`/`worktreeInfo.inLinkedWorktree`, `gitState.currentBranch`, `detectBaseBranch`/`defaultBranch`) and emits it at `flags.workspace` in the prepare output. SKILL.md MUST read the derived value from `flags.workspace` (the `context` object carries **no** `workspace` field); reading any other path is a defect. The default-branch check stays **advisory** (a preflight `warnings.push`, not a halt — `ship.js:882`): on the default branch in the main worktree, the derive returns `branch` and a feature branch is auto-created, so the warning never strands a run. Path-anchoring (`resolveMainWorktree`/`resolveMainWorktreeSafe`/`resolveSdlcRoot`) is **kept** — it anchors `.sdlc/` to the main worktree, which is what makes running inside a user's manual linked worktree correct.
  - Acceptance: "`deriveWorkspace` returns `branch` ONLY for main-worktree + default-branch, and `continue` for (a) any linked worktree and (b) feature-branch-in-main-worktree. Under a derived `branch` run from `main`, `git branch --show-current` returns the NEW branch in ship's main shell BEFORE execute is dispatched, and `state/ship.js read` after migration returns `data.branch === <newName>`. Under a derived `continue` run, no branch is created and no migration runs. The default-branch advisory is a warning, not a halt."

## State model

### Ship state file

- R10: State persistence after each step via `state/ship.js`; cleanup validates pipeline contract before deleting state; state preserved on validation failure
- R73: Session-scoped hook enforcement. Ship state MUST carry a `sessionId` field, stamped with the Claude Code session id whenever a session *claims* the pipeline — on `init` AND on `--resume` (a resumed pipeline re-stamps `sessionId` so the resuming session, not the original one, becomes the enforcing session). The three continuation-enforcement hooks (`pipeline-continue.js` R67, `stop-pipeline-continue.js` R68/R-stop-inprogress-mode-independent, `block-askuserquestion-auto.js` R71) MUST consume a single shared predicate `hookEnforcementAllowed(data, payload)` (`lib/state.js`) — a pure function taking the parsed state object and the hook's parsed stdin payload, returning `{allowed: boolean, reason: string}`, mirroring `pipelineAdvancing(data)`'s shape — as a scoping gate applied BEFORE their own `pipelineAdvancing`-driven logic. The predicate gates SOLELY on stdin `session_id` (from the hook's JSON stdin payload) equalling the state file's `sessionId`. Any missing value (stdin `session_id` absent, or state `sessionId` absent — e.g., a pre-R73 state file) or any mismatch MUST resolve to `false` (no enforcement) — the failure direction is explicit: fail OPEN to silence, never fail CLOSED to blocking, so a hook never enforces against a session it cannot positively confirm owns the pipeline. The predicate MUST NOT compare worktree paths (cwd, `resolveMainWorktree`, or any worktree identifier): linked worktrees legitimately share one main-worktree state directory, and a worktree-path comparison would incorrectly treat a second linked worktree working the same pipeline as a foreign session — worktree identity and session identity are orthogonal, and this gate speaks to the latter only. Omitting this negative clause would read as an oversight and invite re-adding a worktree comparison later; it is intentional and permanent.
  - Acceptance: exec tests in `tests/promptfoo/datasets/ship-hooks-exec.yaml` — `hookEnforcementAllowed (R73): session match allows enforcement (fixture ship-pipeline-session-match)`, `hookEnforcementAllowed (R73): session mismatch resolves to no enforcement (fixture ship-pipeline-session-mismatch)`, `hookEnforcementAllowed (R73): absent sessionId resolves to no enforcement (fixture ship-pipeline-session-absent)`, `hookEnforcementAllowed (R73): resume re-stamps sessionId so a reclaimed pipeline enforces under the new session (fixture ship-pipeline-session-reclaimed)`, `hookEnforcementAllowed (R73): ancient state file with matching sessionId still enforces (fixture ship-pipeline-session-ancient)`, `hookEnforcementAllowed (R73): linked-worktree state shared across worktrees enforces without comparing worktree paths (fixture ship-pipeline-session-linked-worktree)`.
- R-ship-init-prune: At `init` time — before writing the new ship-state file — `state/ship.js cmdInit` MUST remove any pre-existing `ship-<branchSlug>-*.json` files for the same branch in `<mainWorktree>/.sdlc/execution/`. A given branch can only host one active ship pipeline; same-branch state files predating the new init are by definition orphans (e.g., from runs interrupted by context compaction that never reached the terminal `cleanup` step). Pruning is unconditional for same-prefix same-branchSlug files: it does NOT consult the `state.gc.ttlDays` TTL or the branch-existence rule (R39) — those gates apply to cross-branch GC, not to claim-time orphan removal. The prune is implemented via `lib/state.js::pruneStateFiles(prefix, branchSlug)` and runs once per `cmdInit` call before `initState`. The cmdInit JSON output gains a `prunedOrphans: string[]` field (filenames only, not absolute paths) listing every removed file.
  - Acceptance: with one pre-existing `ship-<currentBranchSlug>-*.json` present, `cmdInit` deletes it and the JSON output's `prunedOrphans` array contains exactly that filename; with no pre-existing same-branch file, `prunedOrphans` is empty; pre-existing state files for OTHER branches (e.g., `ship-otherbranch-*.json`) MUST NOT be removed by `cmdInit` — they remain on disk untouched.

- R37: Pre-execute ship state migration. When ship-sdlc derives a new branch name (derived workspace `branch` — main worktree on the default branch), it MUST migrate the ship ledger from the OLD slug (`slugifyBranch` of the ledger's `branch`) to the new branch name in `skill/ship.js`, during `--after branch_prepare` and AFTER the emitted `git checkout -b` has run; the new branch is the live current branch, and `migrateBranchSlug` renames the ledger file and rewrites its `branch`. All other state fields (steps, decisions, deferredFindings, flags, startedAt) MUST be preserved. Migration failures (`migrated: false`, reason `no-state-file` or `same-slug`) are warnings only — the pipeline continues; the orphaned state file will be cleaned by the terminal cleanup step (R38) or by `--gc` (R39). The migration helper `migrateBranchSlug` lives in `lib/state.js` and is exposed via the `migrate` subcommand on `state/ship.js`. When derived workspace is `continue` (linked worktree, or feature-branch-in-main-worktree), migration is skipped silently (no new branch is created).
  - Acceptance: "Ship state file is renamed to match `<newName>` when the derive yields `branch`; migration runs in the main worktree cwd where the OLD slug filename is still resolvable; `state/ship.js read` after migration returns `data.branch === <newName>`. When the derive yields `continue`, no migration runs."
- R39: `/ship-sdlc --gc` on-demand pruning. When `--gc` is passed, `skill/ship.js` MUST short-circuit pipeline composition and emit `{action: "gc", report: {...}, errors: [], warnings: []}` to the prepare-output file. The report shape is `{ttlDays: N, ship: {deleted: [...], kept: [...]}, execute: {deleted: [...], kept: [...]}}` where each entry in `deleted`/`kept` is `{file, prefix, branch, reason}` (prefix ∈ `{"ship", "execute"}`). Pruning rule: a file is deleted iff (mtime is older than the TTL) AND (parsed branch slug does not match any current branch from `git branch --list`); files newer than the TTL are kept regardless (in-flight pipelines must not be wiped). The TTL defaults to `state.gc.ttlDays` from `.claude/sdlc.json` (fallback 7); CLI `--ttl-days <N>` overrides config. The same `gcStateFiles` helper from `lib/state.js` powers both `--gc` and the terminal cleanup step (R38). The skill MUST print the report and stop — no pipeline steps run.
  - Acceptance: `/ship-sdlc --gc` produces a prepare output with top-level `action: "gc"` and a `report` object containing `ship` and `execute` sub-reports each with `deleted[]` and `kept[]` arrays; `/ship-sdlc --gc --ttl-days 0` removes every state file whose branch is absent from `git branch --list` (regardless of age) but never removes files for currently-existing branches; no pipeline step is dispatched.

> **Implementation surface for R37–R39:** `state/ship.js` exposes `gc`, `migrate`, and `cleanup-pipeline` subcommands; `state/execute.js` exposes `gc`. The shared logic lives in `lib/state.js::gcStateFiles` and `lib/state.js::migrateBranchSlug`.

- R-step-result-fields: Resume after compaction fails silently when the state file lacks typed per-step result fields — SKILL.md cannot reconstruct PR URLs, version tags, or review verdicts from the plain step status. Ship state step records MUST carry optional typed fields: `reviewVerdict` (string: `APPROVED | APPROVED WITH NOTES | CHANGES REQUESTED`), `prUrl` (string), `commitSha` (string), `versionTag` (string). `lib/state.js` MUST derive `nextPendingStep` from the step list (first step with `status !== 'completed' && status !== 'skipped'`). SKILL.md Step 4 MUST write result fields via `state/ship.js complete --result-fields <json>` at each applicable step.
  - Acceptance: `state/ship.js complete` accepts `--result-fields <json>` and writes typed fields into the step record; `lib/state.js::nextPendingStep(state)` returns the name of the first non-terminal step; after the version step completes, `state.steps['version'].versionTag` is the tag string emitted by version-sdlc; after the PR step completes, `state.steps['pr'].prUrl` is the PR URL.

### Step lifecycle

- R69: `state/ship.js` MUST provide a `begin-step` subcommand that atomically (a) runs the ship-todos `step` transition for the given step name, (b) records `in_progress` via the existing `start` logic, and (c) prints to stdout a JSON object of the same shape as the ship-todos `--event step` output (`{ todos, marker }`). A `complete-step` subcommand MUST do the same for `complete` + ship-todos mark-completed. Both MUST be idempotent (re-invoking `begin-step` on an already-`in_progress` step does not corrupt state). The shared step-transition and mark-completed logic MUST be reused from `lib/ship-todos.js` (DRY), not duplicated. ## Step composition

### Phases

1. CONSUME — load config, parse flags, run `skill/ship.js` for context detection and step computation
   - **Script:** `skill/ship.js`
   - **Params:** A1-A7, A9-A11 forwarded (`--auto`, `--steps <csv>`, `--quality`, `--bump`, `--draft`, `--resume`, `--init-config`, `--openspec-change`, `--plan <path>`); internal: `--has-plan` (ship-sdlc's own execute-step-eligibility flag — always set by `ship-sdlc/SKILL.md`'s own invocation, not derived from `--plan` or conversation context; see R72/R-PLANFILE for the separate, CLI-only resolution of `context.planFile`).    - **Output:** JSON → P1-P6 (flags with per-flag provenance sources, resume detection, context with branch/auth/openspec/worktree, pipeline steps with status/reason/skipSource/invocation, config)
2. PLAN — build pipeline table from `skill/ship.js` steps array; display flag resolution and auto-skip decisions
3. CRITIQUE — validate pipeline: gh auth, branch safety, skip values, flag coherence
4. DO — present pipeline for confirmation (or auto/dry-run); execute steps sequentially via Agent dispatch
   - **Script:** `state/ship.js`
   - **Params:** subcommands per step lifecycle: `init`, `start`, `complete`, `skip`, `fail`, `decide`, `defer`
   - **Output:** JSON state object persisted to `.sdlc/execution/ship-<branch>-<timestamp>.json` for `--resume` support
5. REPORT — summary table with per-step results, decisions log, deferred findings, state-file cleanup
   - **Script:** `state/ship.js`
   - **Params:** subcommand `cleanup` (on success) or `read` (on failure, state preserved)
   - **Output:** state file removed on success; preserved on failure for `--resume`

- R41: Pipeline MUST support opt-in `verify-pipeline` step inserted after `pr`, gated by step membership in `flags.steps`.

A step that edited source files reports the result of a real project check. The Agent prompt carries only the arguments, the branch and the prior results. - R-expected-branch-injection: `skill/ship.js` MUST append `--expected-branch <featureBranch>` to `step.invocation` for the `commit`, `commit-fixes`, `version`, and `pr` steps. `<featureBranch>` is `state.data.branch` from the ship state file written by `cmdInit` — this is the single source of truth for the branch ship is operating on. When the state file is absent (e.g., first-run pre-init edge case), ship.js falls back to `git branch --show-current`. - R-expected-branch-branch-derive: R-expected-branch-injection's `state.data.branch`/`git branch --show-current` sources are both unavailable at the time `skill/ship.js` prepare runs for a `workspace: branch` derive (R60) — prepare executes BEFORE the `branch_prepare` step of `ship.js` derives the branch name (via `deriveBranchFromPlan`) and runs `git checkout -b`. Consequently, on every fresh `workspace: branch` run, the `--expected-branch` value baked into `steps[commit|commit-fixes|version|pr].args`/`.invocation` by prepare is the pre-checkout branch (typically the default branch), not the feature branch — R-expected-branch-injection's acceptance criterion ("`context.expectedBranch` equals the current feature branch") is unsatisfiable at prepare time for this derive and must be corrected downstream. `skill/ship.js` MUST close this gap in its `--after branch_prepare` call: after `migrateBranchSlug` it recomputes the steps with `expectedBranch` set to the new branch, so every `--expected-branch <value>` in the emitted `steps[].args` and `steps[].invocation` (string-typed only — `cleanup`'s `invocation` is an object and MUST NOT be touched) carries the new branch. This is a one-time correction in `ship.js` (every later `--after` call recomputes the steps from the ledger's branch), not a per-dispatch-site substitution and not a live `git branch --show-current` re-query at each of the four call sites (a live re-query at dispatch time would make the guard tautological — "is current branch equal to current branch" — defeating the branch-drift protection R-expected-branch-injection exists to provide). When the derive is `continue` (no checkout, `EXECUTE_BRANCH` unset), no patch is needed — prepare's `gitState.currentBranch`-derived value is already correct because no branch change occurs. The Step 2 pipeline table is printed before this patch runs and MAY display the stale pre-checkout value; this is expected and is a display-only discrepancy — the steps `ship.js` emits, not the printed table, are what the Step 5 dispatch reads from.
  - Acceptance: For a `workspace: branch` run, after the checkout block executes, re-reading the prepare-output file shows `steps[commit].args`, `steps[commit-fixes].args`, `steps[version].args`, and `steps[pr].args` all containing `--expected-branch <EXECUTE_BRANCH>` (not the pre-checkout branch), and `context.expectedBranch === EXECUTE_BRANCH`. `steps[cleanup].invocation` (object-typed) is unmodified. For a `workspace: continue` run, the prepare-output file is unmodified by this requirement.

- P7: `steps[].agent`, `steps[].model` and `steps[].effort` (strings) — the step's agent (`sdlc:ship-step-<step>`; commit-fixes uses `sdlc:ship-step-commit`) and the model and effort `skill/ship.js` reads from that agent file; inline steps keep a render-only `model`. ## Gates

- G1: `gh` CLI authenticated — `gh auth status` succeeds
- G2: Not on default branch — warn if on main/master (do not block)
- G3: Step values valid — all CLI `--steps` values are recognized step names (`VALID_STEPS` from `lib/ship-fields.js`)
- G4: At least one step will run — pipeline is not entirely skipped
- G5: Flag coherence — `--bump` without version step produces error (exit code 1, blocking). The `--bump` value space accepts `major|minor|patch` or any pre-release label matching `^[a-z][a-z0-9]*$`; values outside this set are rejected at parse time before the version step runs.
- G6: Pipeline contract — every `will_run` sub-skill step was dispatched via the Agent tool (`dispatchMode: 'agent'`); inline-Bash steps emit `dispatchMode: null`
- G6a: Pipeline completion gate — `state/ship.js cleanup` validates all steps are in terminal state (`completed`, `skipped`, or `failed`) before deleting the state file. Steps still `pending` or `in_progress` cause cleanup to refuse deletion and exit 1.
- G7: Staging gap filled — `git add -A -- ':!.sdlc/'` ran between execute and commit
- G8: Rebase attempted — rebase ran after commits, before version (when applicable)

- R3: Pipeline plan is a binding contract: steps with `status: "will_run"` must execute; LLM cannot override
- R5: Skip set provenance tracked via `skipSource`: `cli`, `config`, `auto`, `condition`, `none`; fabrication guard blocks (error, exit code 1) on `default` source
- R-post-version-ancestry: After the version step completes and `NEW_TAG` is known, ship-sdlc MUST verify that the new tag is an ancestor of the feature branch via `scripts/util/verify-tag-ancestry.js --tag <NEW_TAG> --branch <EXECUTE_BRANCH> --remote origin`. On non-zero exit (tag is NOT an ancestor), ship-sdlc MUST abort the pipeline with the error: "Tag `<tag>` is not an ancestor of branch `<branch>`. The release commit landed on a different branch. Delete the tag (`git push origin :refs/tags/<tag>`) and re-run version step on the correct branch." This gate is a no-op when `NEW_TAG` is unset (version step was not in `steps[]`). The check MUST be performed before dispatching the `pr` step; it is the only safeguard against tags silently landing on orphaned commits.
  - Acceptance: when `verify-tag-ancestry.js` exits non-zero for a given tag/branch pair, ship-sdlc halts with the documented error message containing both the tag name and the branch name, plus the `git push origin :refs/tags/<tag>` remediation command; when `NEW_TAG` is unset the block is a no-op and the pipeline continues normally.

- R-INVARIANT-COMPLETENESS: After `execute-plan-sdlc` returns and before ship-sdlc marks the execute step complete, ship-sdlc MUST run `state/execute.js verify-completeness`, within the Scope below, as a blocking invariant check. If the script exits non-zero (exit 65 = missing task IDs; exit 2 = `plannedTaskIds` absent from state or script not found), ship-sdlc MUST mark the execute step `failed`, halt the pipeline, and NOT advance to commit or any subsequent step. Exit 65 produces a structured JSON error on stderr: `{missingIds, totalPlanned, totalAccounted}`; exit 2 indicates a structural state problem (state written before `plannedTaskIds` was recorded, or corrupted init). Note: state files that lack `plannedTaskIds` will trigger exit 2 on any `--resume` attempt; users must start a fresh run rather than resuming from such state files. Scope: the check covers an execute run that ship dispatched and that returned to ship, when an execute state file for the branch exists at that point (a corrupt file counts as existing). When none exists — execute-plan-sdlc's R14 cleanup, which deletes the file only after the same check passed, or the R5 small-plan path, which never writes one — ship-sdlc records the execute step completed without running the check and adds `completenessGate: "no-execute-state"` to that history entry's data. After a pending-question stop, when the user answers `finished` at `execute_handoff`, ship runs the check if an execute state file exists (halting on any non-zero exit); if none exists, ship records execute completed with `source: "user-attested"` in the ledger history and names it in the summary.
  - Acceptance: when `state/execute.js verify-completeness` exits 65, ship-sdlc's pipeline halts with the execute step in `failed` status and does NOT dispatch commit-sdlc; when the script exits 2 (plannedTaskIds missing), ship-sdlc halts with exit 2 before advancing; when the script cannot be located, ship-sdlc exits 2 with the error "Cannot locate execute.js — completeness gate cannot run"; when all tasks are accounted the pipeline advances normally. When `execute-plan-sdlc` returns success and no execute state file exists for the branch, the execute step is recorded completed with `completenessGate: "no-execute-state"` and the pipeline advances to `stage_changes`.

## Prepare script contract

- P1: `flags` (object) — resolved flags with `sources` map showing CLI/config/default provenance per flag
- P2: `resume` (object) — `{ found, stateFile }` resume detection result
- P3: `context` (object) — `{ planFile, planInContext, uncommittedChanges, currentBranch, defaultBranch, ghAuth, openspec, sdlcGitignored, worktree }`. `planFile` is the absolute path to the active plan markdown, resolved solely from `--plan <path>` (R72, C19, R-PLANFILE) — `null` when the `execute` step will not run. `planInContext` reflects the internal `--has-plan` step-eligibility signal (see Workflow Phases, CONSUME) — it does NOT mean a plan was detected in conversation context; it is set unconditionally by `ship-sdlc/SKILL.md`'s own prepare invocation and is independent of whether `planFile` is populated.
- P4: `steps` (array) — pipeline steps, each with `{ skill, status, reason, skipSource, args, invocation, pause }`
- P5: `steps[].invocation` (string) — exact skill name + computed args for Agent dispatch
- P6: `config` (object | null) — ship config from `.sdlc/local.json` or null if absent
- P8: `migration` (object | null) — `{ project: { schemaVersion, migrated, backupPath, stepsApplied }, local: { ... } }` after `verifyAndMigrate` runs at pipeline entry. Null only when both calls were short-circuited by `SDLC_SKIP_CONFIG_CHECK=1` or `--skip-config-check`. On migration failure, `migration` is null AND `errors[]` carries the failing step identifier.

## Failure handling and resume

- E1: Sub-skill fails (script crash) → stop pipeline, save state for `--resume`; sub-skill handles its own error reporting
- E2: `gh auth status` fails → stop at validation, tell user to `gh auth login`
- E3: `git add` fails → stop pipeline, show error
- E4: Network error (gh API) → auto-retry 3 attempts with exponential backoff; if exhausted, save state
- E5: State file write fails → warn and continue (best-effort)
- E6: Resume state file corrupt → warn, start fresh
- E7: Review verdict unparseable → treat as APPROVED WITH NOTES, warn user
- E8: Rebase conflict → abort rebase; auto mode stops, interactive offers pause/skip/merge options
- E9: Sub-skill times out → stop pipeline, save state

- R-config-failure-mode: A migration failure halts the pipeline before step 1 — no partial pipeline runs. The prepare output is the single point of refusal: SKILL.md gates Step 4 (DO) on `errors.length === 0` from the prepare output. If a previous run partially migrated and the lock file (`.sdlc/.migration.lock`) is stale, the prepare surfaces a `ConfigMigrationLocked` error with PID guidance; the user is responsible for removing the lock manually after confirming no other migration is in flight.

- R48: `verify-pipeline` timeout MUST produce a warning log; pipeline MUST exit 0 (warning, not error) and continue to `await-remote-review`.
- R49: `--resume` after `verify-pipeline` exhaustion (timeout, abort, or cap) MUST NOT re-poll; tracked via state-file marker `verifyPipelineExhausted: true`.
- R54: `await-remote-review` timeout MUST produce a warning log; pipeline MUST exit 0 (warning, not error).
- R55: `--resume` after `await-remote-review` exhaustion MUST NOT re-poll; tracked via state-file marker `awaitRemoteReviewExhausted: true`.
- R64: When `/ship-sdlc` is invoked while plan mode is active, the prepare script (invoked from SKILL.md Step 0 with `--plan-mode-blocked`) MUST resolve all CLI/config flags as usual, compute the canonical `steps[]` array, and persist an init state file at `<stateDir>/ship-<branchSlug>-<timestamp>.json` via `lib/state.js initState` with every step in `pending` status and the resolved `flags` snapshot (including `bump`, `steps`, `preset`, etc.). The output JSON MUST include `flags.planModeBlocked: true` and `stateFile: <path>`. On the user's next `/ship-sdlc` invocation (after exiting plan mode), the existing implicit-resume mechanism (`detectResumeState` → `flags.implicitResume`) picks up the state file and resumes from the first pending step with the originally-resolved flags.

## Invariants and constraints

- R19: Prepare script output is the single authoritative source for all contracted fields (P-fields) — script-provided values take unconditional precedence over skill-generated content, and all factual context (git state, config, flags, metadata) must originate from script output to ensure deterministic behavior
- R-projectroot-ship: Scripts invoked from a worktree or sub-directory can silently operate on the wrong project root when using `process.cwd()`. All projectRoot resolutions in ship-sdlc's scripts (`skill/ship.js`, `state/ship.js`, and any lib helper they invoke) MUST route through `resolveSdlcRoot()` (from `lib/config.js`); `process.cwd()` is forbidden as a project-root source except in documented bootstrap entry points.
  - Acceptance: `resolveSdlcRoot` is called at the top of `skill/ship.js` and `state/ship.js`; no bare `process.cwd()` usage appears in any path that contributes to `projectRoot`; calling scripts from a worktree sub-directory yields the same `projectRoot` as calling from the main repo root.

- R-progressive-disclosure: To bound the resident context footprint of `ship-sdlc/SKILL.md`, rarely-hit and reference branches MUST live in on-demand companion docs that SKILL.md instructs the LLM to Read only at the point the branch is entered — never preemptively. This mirrors the established pattern in `execute-plan-sdlc` (`classifying-and-waving-tasks.md`, `wave-runner-template.md`, `recovering-from-failures.md`). The canonical companion file set under `plugins/sdlc-utilities/skills/ship-sdlc/` is exactly five files: `entry-modes.md` (entry-mode handlers `--init-config`, `--gc`, dry-run), `reference.md` (Error Recovery, Learning Capture, Gotchas, DO NOT, and the judgment sections of the inline steps `verify_pipeline`, `await_remote_review` and `learnings_commit`), `config-format.md` and `state-format.md` (reference formats) and `openspec-steps.md` (verify-openspec/archive-openspec steps). Adding another requires amending this requirement. (The former `workspace-worktree.md` is removed — workspace is auto-detected per R60, so there are no config-gated worktree-mode branches to extract.) The contract has two parts:
  1. **Cold / reference branches** (entry-mode handlers `--init-config`, `--gc`, dry-run; plus Error Recovery, Learning Capture, Gotchas, DO NOT) live in `entry-modes.md` and `reference.md`. SKILL.md replaces each with a ≤2-line gated pointer ("If `--gc` was passed → Read `./entry-modes.md` (gc section) and follow it. Do not read preemptively.").
  2. **Common-path behavior is unchanged.** Extraction relocates instructions; it does not alter the executed flow. A no-flag `ship it` walkthrough MUST NOT instruct reading `entry-modes.md` or `reference.md`. The branch-mode-active post-version ancestry HARD GATE (fires when `NEW_TAG` is set) MUST stay fully inline. The cold-vs-warm tiering is intentional and load-bearing: future edits MUST NOT silently re-inline these branches into SKILL.md.
  - Acceptance: the five companion files exist under `plugins/sdlc-utilities/skills/ship-sdlc/`; `workspace-worktree.md` does NOT exist; each extracted section in SKILL.md is a ≤2-line gated Read pointer; a no-flag walkthrough reads neither companion file; `--gc` / `--init-config` / dry-run read `entry-modes.md`, and reference material (recovery/gotchas) is read only on the relevant trigger.

- C1: Must not deviate from per-step `dispatchMode`. Every sub-skill step (including `execute-plan-sdlc`) is Agent-dispatched. The LLM must not override `steps[].dispatchMode`.
- C2: Must not skip critique step (Step 3)
- C3: Must not forward `--auto` to sub-skills that don't support it (execute-plan-sdlc, review-sdlc)
- C4: Must not automatically resolve review findings — received-review-sdlc handles this
- C5: Must not run pipeline steps in parallel — strictly sequential
- C6: Must not delete state file on failure — needed for `--resume`
- C7: Must not proceed past a failed sub-skill — stop, save state, inform user
- C8: Must not skip steps marked `will_run` in the pipeline plan — the plan is a binding contract
- C9: Must not copy example args from SKILL.md — use `step.invocation` from skill/ship.js
- C10: Must not add `--steps` flags not present in user invocation; pipeline composition derives from CLI `--steps` > config `ship.steps[]` > `BUILT_IN_DEFAULTS.steps`
- C11: Must not skip, bypass, or defer prepare script execution — the script must run and exit successfully before any skill phase begins
- C12: Must not override, reinterpret, or discard prepare script output — for every P-field, the script return value is authoritative and final; the skill must not substitute LLM-generated alternatives
- C13: Must not independently compute, infer, or fabricate values for any field the prepare script is contracted to provide — if the script fails or a field is absent, the skill must stop rather than fill in data
- C14: Must not re-derive data the prepare script already computes via shell commands, tool calls, or LLM inference — script output is the sole source for all factual context, preserving deterministic behavior
- C15: The LLM must not add, remove, or change the steps[].isolation field when dispatching Agents in Step 5. Isolation comes verbatim from ship.js prepare output, or is omitted when ship.js emits null (Agent tool schema enum forbids passing null).
- C16: The LLM must not override `steps[].dispatchMode`. If `'agent'`, invoke via Agent tool with `subagent_type: step.data.agent` and, when non-null, `isolation: step.data.isolation`; never pass `model` or `effort` — the agent file pins them. If `null`, the step is an inline-Bash operation. The value `'skill'` is no longer valid — every sub-skill step uses `'agent'`.
- C18: The `block-askuserquestion-auto.js` PreToolUse hook must degrade silently (exit 0, no output) on any failure (no stdin, parse error, no git, no ship state file, lib load failure) and when `flags.auto !== true` — it must never block `AskUserQuestion` outside an active `--auto` ship pipeline.
- C19: No plan-path autodiscovery in any ship code path. `ship.js` MUST NOT scan a plans directory, read a plan-path setting from any project or global settings file, or otherwise infer `context.planFile` by any means other than the explicit `--plan <path>` CLI flag (R-PLANFILE, R72).
